## 2. Устранить неверный смысл времени

`RiskWorkspace.vue` считает `now - dueAt` и называет это «Ожидание».
В backend `backend/internal/risk/domain/no_response.go:19` dueAt вычисляется как
время сообщения плюс рабочий порог. Это НЕ начало ожидания.

Для пилота не вычислять рабочее ожидание из календарного времени, не разбирать
порог из текста reason и не брать произвольное последнее сообщение за trigger.
Показывать доступный факт: «Срок по правилу» + абсолютный `dueAt`, рядом «Риск
обнаружен» + `detectedAt`, в часовом поясе организации. При отсутствии даты —
нейтральное отсутствие значения. Универсальное «Срок ответа не наступил» удалить:
не каждый тип риска относится к сроку ответа. Живой таймер ожидания до появления
достоверного начала/рабочей длительности не показывать. Проверить хотя бы
NO_RESPONSE и другой тип, future/null даты, закрытый риск.

## 3. Принятые решения для пилота вместо повторных вопросов

- Статус-вкладки сделать **без чисел**. API фильтр уже есть: «Все активные» →
  `active=true`; «Новые» → `status=OPEN`; «В работе» →
  `status=ACKNOWLEDGED&status=ACTED`. `active` и `status` не отправлять вместе.
  ACTED сохраняет отдельный статус и входит в рабочую группу. Не считать totals
  по загруженной странице и не делать N запросов ради декоративных счётчиков.
  Обновить URL/parser, query keys и сброс cursor. Вкладки фильтруют ленту;
  денежная сводка сохраняет текущую семантику и НЕ получает status/active.
  Добавить проверки запроса, back/reload, смены фильтра/организации, пагинации.
- Под организацией допустимо «N точек», если список успешно получен; город и
  часовой пояс вместо города не сочинять. Ошибка/отсутствие данных не равны нулю.
- Telegram badge: `facts.liveConnections > 0` не доказывает исправность Telegram
  (учитывает другие провайдеры и ERROR). `telegramLinked` — личная привязка.
  Зелёный статус допустим только по разрешённому ответу конкретной интеграции/health;
  без таких данных скрыть статус либо оставить нейтральный вход к источникам.
  Для неизвестного/ошибочного состояния успешный статус не показывать. Не выполнять
  запрещённые роли запросы и не запускать новый запрос на каждом переходе.
- В контексте детали показывать имя точки по `risk.locationId` и разрешённому
  GET /locations, как уже сделано для ленты. Канал остаётся подписью переписки.
  При неизвестной точке не выдавать имя канала за имя точки.
- Денежные подписи сохранить: «Потенциальная выручка» и «Подтверждённо
  возвращённая выручка» с подписью «За всё время». Не добавлять «за 7 дней», число высоких рисков и другие
  отсутствующие показатели. Честный перенос текста — допустимое отличие от Figma.
- Копию заголовков/форм/этапов брать из утверждённого дизайна при сохранении
  смысла, команд и прав. Это перенос UI, а не изменение бизнес-сценария.
- В действии/исходе оставить disabled до выбора по макету; дать понятную
  доступную подсказку выбора, сохранить валидацию длины заметки, busy, ошибки и
  защиту от повторов. В локальной карте приёмки явно заменить проверку клика по
  пустой форме (US-M08-02/04 шаг 2) проверкой disabled → выбор → доступная отправка.
- Перенос подробных дат и Telegram-действия из карточки ленты в деталь допустим
  для UI v2, если они доступны в детали. Правильная ссылка старого сценария —
  **US-M07-01 шаг 4**, не US-M07-03. Не отмечать старый буквальный шаг как PASS:
  записать соответствие новому пути. Backend user-stories не редактировать.
- История этапов доступна только с разрешённым правом. Заметка действия после
  reload отсутствует в `RadarAction` контракта: не подделывать сохранность через
  localStorage/fixture-only данные. Полное чтение заметок/исходов отложено после
  релиза и не блокирует текущий F04. Сейчас перечитываются действия с типом/временем
  и последний исход сделки; UI не обещает полной истории. Детали — RELEASE-SCOPE.
- Остальной Access и акцентный detail не являются блокерами F01/F02.

Зафиксировать эти решения в локальной acceptance mapping и DEPENDENCIES.
Это условия реализации пилота; они не означают, что G01 уже принят.

## 6. Порядок и критерии сдачи

Один Sonnet владеет правками. Порядок: источники/семантика → адаптивы/вкладки →
evidence harness → проверки. Два read-only reviewer только на зафиксированном
финальном diff, параллельно; передать этот brief, точные файлы, story mapping,
готовые изображения и логи. Не заставлять каждого повторно выгружать Figma.
После исправлений повторять затронутый review. Финальные изменения после review
нельзя объявлять проверенными прежним verdict.

- Адресные unit/E2E на исправления, затем `npm run check`.
- `npm run build:dev`, `npm run build:pre-prod`, `npm run build:prod`,
  `npm run audit:release` с реальными exit codes.
- Установить отсутствующие браузеры `npx playwright install firefox webkit`.
  Выполнить штатные mock-проекты: `npm run test:e2e -- --project=chromium
--project=firefox --project=webkit --project=mobile`. Проект `stand` не запускать
  автоматически: реальный backend и внешние действия — отдельная проверка.
- Responsive/a11y: штатные ширины, 390/834/1440, длинные строки, keyboard/focus,
  zoom/reflow, открытие/закрытие меню/фильтров, доступность disabled/ошибок.
- Повторить visual capture после финальных изменений. Приложить reference/actual/
  diff и описание допустимых расхождений. Сохранять в artifacts, не test-results.
- Обновить STATUS, source-map, DEPENDENCIES и reviewer verdicts. Старые итоги
  явно пометить историческими, а не оставлять параллельно противоречащими текущим.
- Финал: короткая таблица «исправлено / проверено / ограничение», команды/коды,
  привязка к финальному diff, ссылки на картинки и порядок ручного просмотра
  login → Radar → фильтры → detail → взять в работу → назад/reload.

Цель — **готов к пользовательской приёмке G01**, не «пользователь принял».
Реальный backend, отсутствующие поля контракта и окончательное пользовательское
решение честно отделить от mock/frontend PASS. При оставшемся локальном FAIL
не объявлять пилот полностью готовым и не переходить к F03.
