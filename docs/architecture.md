# Архитектура

## Слои и правила

Направление зависимостей: `app → pages → widgets → features → entities → shared`. Модуль импортирует только нижние слои; слайсы одного слоя друг друга не видят. Внешний импорт слайса идёт через его `index.ts`, внутри слайса — относительные пути. Сегменты — только `ui`, `api`, `model`, `lib`, `config` (правило Steiger `segments-by-purpose`).

| Слой       | Слайсы                                                                                            |
| ---------- | ------------------------------------------------------------------------------------------------- |
| `app`      | `main.ts`, `App.vue`, `providers/` (query client, контекст API), `router/`, `layouts/`, `styles/` |
| `pages`    | `login`, `register`, `workspaces`, `onboarding`, `radar`, `not-found`                             |
| `widgets`  | `app-shell` (боковая навигация, мобильное меню), `radar-summary`, `risk-feed`                     |
| `features` | `auth-session` (вход, регистрация, выход), `select-workspace`, `create-organization`              |
| `entities` | `session`, `organization`, `location`, `risk`                                                     |
| `shared`   | `api`, `config`, `lib`, `ui`                                                                      |

Границы проверяют два инструмента: Steiger (`npm run lint:fsd`) и локальное ESLint-правило `tooling/eslint/fsd.mjs` для import, dynamic import и re-export. Правило `insignificant-slice` отключено: слайсы создаются под будущие блоки, а не под текущее число использований.

## Контракт и транспорт

Типы DTO вручную не пишутся. `contracts/openapi.yaml` — снимок контракта backend (`contracts/source.json` хранит commit и время синхронизации), `npm run api:generate` превращает его в `src/shared/api/generated/schema.d.ts`, а `npm run api:check` в CI следит, что типы не разошлись со снимком.

`shared/api/client`:

- `create-client.ts` — `openapi-fetch` с `credentials: 'include'`, таймаутом и промежуточным слоем: запрет машинных путей (`/internal/*`, `/api/v1/webhooks/*`), `X-Request-ID`, `Accept`, проверка обязательного `X-Tenant-ID` у tenant-scoped операций и его совпадения с выбранной организацией. После ответа слой распознаёт потерю сессии (`401` на защищённом пути) и вызывает хук контекста; `401` на формах входа и `/auth/me` остаются обычными ошибками.
- `unwrap()` — превращает результат в данные либо `ApiError`; сетевые сбои и таймауты получают `httpStatus: 0`, отмена вызывающей стороной пробрасывается как есть.
- `api-error.ts` — единый `ApiError` (код, статус, `traceId`, `retryAfterSeconds`). Серверное `message` никогда не показывается пользователю: подписи подбирает `messages.ts` по коду и статусу, а `traceId` доступен в технических деталях.
- `context.ts` — `ApiContext` (`tenantId()`, `onSessionLost`). `shared` не знает о хранилище сессии, поэтому слой `app` явно устанавливает контекст при старте (`app/config/api-context.ts`).
- `query.ts` — соглашения TanStack Query: `tenantScope(tenantId)`, `normalizeFilters`, `shouldRetryRead`.

## Состояние

- **Pinia** хранит только сессию (`entities/session`): пользователь, членства, выбранная организация, статус загрузки, причина выхода. Выбор организации запоминается в `localStorage` по идентификатору пользователя и при загрузке сверяется с членствами; чужой или устаревший идентификатор удаляется.
- **TanStack Query** хранит все серверные данные. Ключи tenant-scoped запросов начинаются с `['tenant', tenantId]`; смена организации (`features/select-workspace`) отменяет и удаляет запросы прежней организации до переключения, поэтому данные одной организации не появляются под именем другой. Настройки клиента — `app/config/query-client.ts`: повтор только сетевых и `5xx` ошибок чтения, мутации не повторяются.
- Локальное состояние страниц (фильтры Radar) живёт в query-строке маршрута: перезагрузка и ссылка сохраняют выбор, неизвестные значения отбрасываются.

## Команды и идемпотентная отправка

Мутации не обновляют бизнес-состояние оптимистично: применяется ответ сервера и повторное чтение. После команды инвалидируются ключи по таблице архитектуры frontend (`entities/risk/api/invalidate.ts`): карточка `['tenant', id, 'risk', riskId]`, все ленты `['tenant', id, 'risks']` и сводка `['tenant', id, 'radar']`; исход дополнительно затрагивает `opportunity` и `analytics`.

Действие и исход — append-only записи с заголовком `Idempotency-Key`. `shared/api/client/idempotency.ts` описывает черновик `{ key, body, state }`: ключ создаётся до первого POST; при неизвестном результате (сеть, таймаут, `5xx`) повтор идёт тем же ключом и телом; новый ключ появляется только после однозначного ответа, отмены или изменения тела. Composable `useIdempotentMutation` реализует это поведение с защитой от двойной отправки, а `unwrapWithStatus` отличает `201` (первая запись) от `200` (повтор прежнего результата), чтобы интерфейс не заявлял вторую запись. `409 IDEMPOTENCY_CONFLICT` не повторяется.

Команды без тела (взять в работу, закрыть, рекомендация) идемпотентны на сервере сами по себе и идут через `useRiskCommand` на TanStack `useMutation`. Кнопки показываются по последнему снимку и правам роли (`isActiveRiskStatus`, неизвестный статус команды не активирует), но окончательное решение принимает сервер: после ответа карточка перечитывается и кнопки пересчитываются. Переход во внешний канал записывается как действие `OPEN_CONVERSATION` только после клика по реальной ссылке сервера.

Исход принадлежит сделке (`POST /opportunities/{id}/outcomes`), но записывается из рабочего пространства риска, поэтому команда пока живёт в `entities/risk`; с появлением страницы сделки (этапы) она переедет в `entities/opportunity`.

Подтверждение оплаты (`entities/revenue`, `features/confirm-revenue`, макет 13) создаёт одно неизменяемое событие выручки и одну атрибуцию. Сумма вводится человеком и нормализуется `parseAmount` (`31 000,00` → `31000.00`), валюта по умолчанию — валюта сделки. Для «возвращённой выручки» цепочка риск → действие → исход подставляется только из снимка карточки (`RevenueEvidence`); без действия или исхода вариант недоступен, а окно 30 дней и принадлежность сделке окончательно проверяет сервер (`400`). `409 RECOVERED_ALREADY_ATTRIBUTED` показывает предложение сохранить оплату как обычную, но переключает тип только по явному нажатию пользователя и отправляет новый ключ, потому что тело изменилось. На время запроса диалог не закрывается (`UiDialog dismissible=false`), чтобы черновик с ключом не потерялся; неизвестный результат переживает закрытие диалога до повтора или отмены.

Вердикт по риску (`features/risk-feedback`, `POST /risks/{id}/feedback`) — append-only факт без ключа идемпотентности: защита от двойной отправки только через pending. «Ложное срабатывание» требует причину; на активном риске запись идёт через диалог подтверждения, потому что сервер закроет риск, а причина `NOT_A_LEAD` закроет и сделку как потерянную — интерфейс предупреждает об обоих каскадах и не моделирует их локально. После ответа инвалидируются карточка, ленты, сводка, сделка, точность и аналитика; результат показывает `datasetEligible` — попадёт ли запись в набор для обучения по согласию организации на момент записи. Контракт не отдаёт список вердиктов, поэтому после перезагрузки панель снова предлагает форму.

## Этапы сделки

Сделка читается отдельным запросом `GET /opportunities/{id}` (`entities/risk/api/opportunity-api.ts`): только в нём есть полная неизменяемая история этапов, которую карточка риска показывает от новых к старым с источником перехода (правило, AI, вручную, импорт) и уверенностью модели, если она есть. Матрица переходов (`entities/risk/model/stages.ts`) повторяет модель данных: с активного этапа — любой следующий активный или `LOST`, из `BOOKED` — `WON` или `LOST`, из закрытых — только `ARCHIVED`; назад, тот же этап и преждевременный `WON` не предлагаются. Ручной перевод (`features/change-opportunity-stage`) — `PATCH {stage}` без оптимизма: после `200` инвалидируются сделка, карточка, ленты, сводка и аналитика; закрывающие переходы подтверждаются диалогом с последствиями (выигрыш не фиксирует оплату — она подтверждается отдельно). `409 INVALID_STAGE_TRANSITION` объясняется как уже изменившийся этап, сделка перечитывается, выбор сбрасывается; успех не заявляется. Контроль доступен роли с `opportunity.manage`, окончательное решение принимает сервер.

## Загрузка и маршрутизация

1. `App.vue` показывает нейтральный загрузчик, пока хранилище сессии не выполнило `bootstrap()` (один запрос `/auth/me`); ошибка сети даёт экран с повтором, `401` — гостя.
2. `app/router/guards.ts` перед каждой навигацией ждёт `bootstrap()` и применяет `meta.access`: `guest` (вход/регистрация; авторизованный уходит в Radar), `session` (нужна сессия), `tenant` (нужна выбранная организация: без членств — создание организации, с несколькими — выбор пространства).
3. `meta.permission` проверяется в `ShellLayout`: без права раздел показывает «доступ ограничен», а навигация (`widgets/app-shell`) скрывает недоступные пункты. Права рассчитываются из роли членства (`entities/session/model/permissions.ts`) и служат только для интерфейса; границей доступа остаётся сервер.
4. Путь возврата после входа (`?redirect=`) принимается только внутренний (`shared/lib/return-path.ts`).
5. Потеря сессии: хук `onSessionLost` помечает сессию истёкшей, очищает кеш запросов и переводит на вход с путём возврата. Повторного `/auth/me` в ответ на `401` нет, цикл обновлений невозможен.

## Поток сигналов (SSE)

`GET /api/v1/events` читается streaming `fetch` (`shared/api/client/sse.ts`): нативный `EventSource` не передаёт обязательный `X-Tenant-ID`. Парсер инкрементальный, по правилам EventSource (`event`, `data`, `id`, `retry`, комментарии-heartbeat), с ограничением буфера; сырые фрагменты не логируются. Неуспешный ответ (`401`, `403`, `503 UNAVAILABLE`) становится `ApiError`.

`RealtimeConnection` (`shared/api/client/realtime.ts`) ведёт состояния `connecting → open → backoff/offline → stopped`: повтор с экспоненциальным backoff и jitter (1–30 с) только когда браузер онлайн и вкладка видима; тишина дольше 45 с считается обрывом; `401`/`403` останавливают поток до смены контекста. После любого переподключения потребитель получает `RECONNECTED`, потому что события за разрыв потеряны.

Слой `app` (`app/config/realtime.ts`) держит один поток на выбранную организацию: сигнал `risk.*` инвалидирует карточку, ленты и сводку через `invalidateRisk`, `resync.required` и переподключение — весь префикс `['tenant', id]`. Кеш вручную не правится, SSE — ускоритель, а не источник истины: `refetchOnWindowFocus`, `refetchOnReconnect`, время последнего снимка и ручное обновление остаются. Состояние потока передаётся интерфейсу через `provide(REALTIME_STATE_KEY)`; индикатор в шапке говорит о канале обновлений («онлайн», «недоступны: обновляйте вручную», «нет сети»), но никогда не утверждает, что данные актуальны.

## Диалоги

Переписки только для чтения (`entities/conversation`, `widgets/conversation-list`, `widgets/conversation-thread`, макет 06). Список — курсорный запрос с фильтрами в query-строке (`search`, `withRisk`, `locationId`, `connectionId`, `status`); поиск и «с риском» выполняет сервер по всему набору организации, локальная фильтрация загруженных страниц запрещена, ввод поиска откладывается на 300 мс. Строка уже содержит контакт, канал, превью и активные риски — запросов деталей на строку нет. Подпись контакта строится с маскированием: имя → часть телефона → часть почты → «Без имени» (`shared/lib/privacy.ts`).

Переписка загружает детали и первую страницу сообщений параллельно. Сообщения приходят от новых к старым; окно разворачивается в хронологию (`orderOldestFirst`), делится по дням в поясе организации, более ранние подгружаются сверху с сохранением якоря прокрутки (`anchoredScrollTop`). Направление читается по подписи автора, а не только по выравниванию; удалённое у поставщика сообщение показывает заглушку; вложения — метаданные без ссылки на скачивание, поэтому всегда «недоступны». Composer отсутствует намеренно: переход во внешний канал — только по `externalLink.url` сервера. На узком экране список и переписка — отдельные состояния маршрута с возвратом к списку.

## Начало работы и настройки

Статус начала работы — только серверный (`GET /organization/onboarding`): `nextStep` и `steps[].done` выводятся из данных, localStorage не участвует. `/onboarding` перечитывает статус и ведёт на нужный шаг (`pages/onboarding/model/steps.ts`), после каждого шага статус инвалидируется; напоминание на Radar (`OnboardingBanner`) появляется только у владельца и только пока статус неполон. Шаг источника сообщений подключает источник прямо на странице тем же диалогом, что и «Интеграции»: пока источника нет, это главное действие шага, а выход в Radar подписан «Подключу позже» и не главный. Необязательный шаг личной привязки Telegram выполняется картой привязки на той же странице со вторичной кнопкой; настройка не объявляется завершённой, пока обязательные шаги не выполнены. Нумеруются только обязательные шаги, необязательный отмечен значком. Если источник не подключён, пустая лента Radar говорит об этом и ведёт к подключению, а не пишет «всё под контролем».

Недельный график (`entities/location/model/hours.ts`) хранится черновиком из семи дней и уходит одним атомарным PUT: у выходного нет скрытого времени, у рабочего дня обе границы и `opensAt < closesAt`; проверка локальная, окончательная — серверная. Несохранённый черновик защищён подтверждением при смене точки и уходе со страницы. В мастере у редактора нет своей кнопки: «Сохранить и продолжить» вызывает `save()` редактора и переходит дальше только после успешного сохранения. У времени видимые подписи «с» и «до», а «Применить время» копирует время первого рабочего дня на остальные. Форма организации отправляет только изменённые поля и подтверждает смену пояса или валюты, объясняя последствия для аналитики и исторических сумм. Услуги: пустая цена — `null`, а не ноль; диапазон не сводится к средней; отключение — `DELETE` с подтверждением, включение — `PATCH active=true`; список и фильтры строятся на клиенте из полного каталога.

## Интеграции источников

Подключения (`entities/integration`, макет 08) — только для владельца. Секреты write-only: токен бота Telegram проверяется по формату контракта, уходит один раз в `POST /integrations/{provider}/connect` и очищается из формы после любого ответа; секрет webhook либо задаёт пользователь, либо выпускает сервер и возвращает единственный раз — диалог показывает его с кнопкой копирования и уничтожает при закрытии. `ACTIVE` означает успешную проверку у провайдера, `ERROR` — подключение создано, но удалённая настройка не завершилась (код объясняется безопасной подписью, неизвестный код показывается как есть). При `503` черновик без секретов остаётся, пока диалог открыт. Отключение — `DELETE` с подтверждением и обязательным перечитыванием списка после любого ответа: `503` означает «отключено локально, удаление вебхука у провайдера не подтверждено», и подключение не возвращается в активные. «Проверить связь» вызывает `POST …/health/check` и различает `REMOTE` (провайдер опрошен) и `LOCAL` (сохранённое состояние); карточка подписывает время чтения снимка здоровья. Подключение закрывает шаг «Источник сообщений» онбординга через перечитанный серверный статус. Для тех, кто подключает впервые, у поля токена есть раскрывающаяся инструкция «Где взять токен бота», после подключения Telegram названо последнее действие в самом Telegram, а webhook помечен вариантом для разработчика: инструкция адресована ему и копируется целиком без секрета.

## Уведомления и личная привязка Telegram

Личная привязка (`entities/notification`, `features/link-telegram`, макет 05) — ресурс пользователя в организации, а не подключение источника: у неё свои запросы и своё отключение, которое не трогает бизнес-интеграцию. Одноразовая ссылка выпускается `POST /notifications/telegram-link-token`, живёт 15 минут и хранится только в памяти composable; в `href` попадают лишь схемы `https:` и `tg:`, ссылка открывается в новой вкладке с `rel="noopener noreferrer"`. После выпуска статус опрашивается ограниченно: пока вкладка видима, до истечения ссылки и не более 24 попыток с шагом 5 с; кнопка «Проверить привязку» доступна всегда, истёкшая ссылка требует новой. Успешная привязка кладёт статус в кеш и перечитывает серверный статус онбординга (необязательный шаг `TELEGRAM_LINK`). Идентификаторы Telegram интерфейсу не отдаются и не показываются.

Настройки уведомлений (`features/edit-notification-preference`, `/settings/notifications`, макет 11) — пять строк по типам риска; каждая редактируется отдельно и уходит полным `PUT /notifications/preferences/{riskType}`, сброс — `DELETE` с подтверждением и перечитыванием. `isDefault` различим бейджем «По умолчанию» / «Настроено вами». Тихие часы требуют обе границы и их различие; конец раньше начала — интервал через полночь, подписанный явно; время сводки и тихие часы трактуются в поясе организации. Канал Telegram без личной привязки сопровождается предупреждением, но сохраняется — окончательное решение за сервером. Перечитывание списка после сохранения одной строки не стирает черновики остальных (`samePreference`). Раздел доступен владельцу и менеджеру: вкладки настроек строятся по правам, `/settings` ведёт менеджера сразу к уведомлениям, пункт «Настройки» виден каждому участнику, разделы владельца по прямому адресу показывают отказ.

## Команда

Экран «Команда и доступ» (`/settings/team`, макет 12) доступен только владельцу (`member.manage`); список участников — `GET /organization/members`, а не `/auth/me`, где лежат лишь членства текущего пользователя. Слайсы блока сгруппированы: `features/team/{invite-member,manage-member,revoke-invitation,accept-invitation}` — группа без своего `index.ts`, каждый слайс со своим публичным API (локальное правило ESLint и Steiger понимают группы). Приглашение — одноразовый код на 7 дней (ADR 0045): `POST /organization/invitations` возвращает код единственный раз, диалог показывает его с копированием и уничтожает при закрытии; список приглашений кода не содержит, заметка владельца принимающему не показывается. Письма LidRadar не отправляет, код передаёт владелец.

Смена роли и отзыв доступа подтверждаются диалогом с именем, почтой и последствиями; единственный активный владелец на клиенте не понижается и не отзывается (пояснение под кнопками), сервер защищает `409 LAST_OWNER` — при гонке диалог показывает конфликт, не заявляет успех, список перечитывается после любого ответа. Отозванный участник остаётся в списке как «Доступ отозван» с датой: на него ссылаются факты. Действия над собой завершают контекст безопасно: после собственного понижения перечитывается сессия и открывается раздел, доступный новой роли; после отзыва собственного доступа запросы организации отменяются и убираются из кеша, затем перечитывается `/auth/me`, и guard ведёт к оставшимся пространствам или созданию организации. Приём кода — `POST /invitations/accept` сеансом без `X-Tenant-ID` (`/invitations/accept`, ссылки с экранов выбора пространства и создания организации); код нормализуется от пробелов, после `200` обязательно перечитывается `/auth/me`, членство не собирается на клиенте; `404` объясняется нейтрально, `409 ALREADY_MEMBER` ведёт к списку пространств.

## Аналитика и точность

`/analytics` (макет 07) — только для `analytics.read` (владелец). Окно — две включительные календарные даты организации в query-строке (`from`, `to`); по умолчанию последние 30 дней, включая сегодняшний день организации, поэтому запросы стартуют после загрузки организации и не выполняются дважды. Локально проверяются формат, порядок и предел 366 дней; при ошибке блоки не запрашиваются. Три запроса независимы (`entities/report`): `GET /analytics/summary` и `GET /analytics/payments` получают даты как есть, `GET /risks/precision` — моменты UTC, вычисленные как начало календарного дня организации для начала окна и начало следующего дня для конца (`zonedDayStart`, с учётом переходов на летнее время). Ответный `period` авторитетен и подписывает экран вместе с UTC-границами. Сбой одного запроса показывает ошибку только своего блока.

Показатели не досчитываются: деньги берутся из `revenue` в валюте ответа, число возвращённых оплат — из `attribution`, доли считаются только при ненулевом знаменателе (`ratio`), `precision = null` подписывается «Недостаточно данных», `reliable = false` — бейджем «низкое покрытие». `potential` подписан как оценка открытых сделок, не выручка. График возвращённой выручки — SVG-столбцы строго по дневному ряду сервера (одна точка на дату, нули на месте, без интерполяции) с таблицей для читателей экрана; длинные окна прореживают подписи дат, не данные. Таблица оплат — курсорная подгрузка, каждая строка со своей валютой, суммы разных валют не складываются; связь с риском ведёт в карточку. Ключи запросов начинаются с `analytics` и `precision`, поэтому команды по риску (`invalidateRisk`) обновляют экран.

## Данные и согласие на обучение

`/settings/privacy` (блок 12, макет 25) — вкладка «Данные» видна каждому участнику: статус `GET /organization/ml-consent` читает и менеджер, выдаёт и отзывает согласие только владелец (`entities/consent`, `features/manage-consent`). Область согласия — наборы данных: реальные переписки и вердикты по рискам для обучения и оценки моделей; работа сервиса от него не зависит, и текст экрана говорит об этом прямо. Обе команды идемпотентны: повторная выдача отвечает `200` вместо `201`, и интерфейс сообщает «уже действовало»; отзыв — всегда `204`. Каждое действие подтверждается диалогом, чей текст не обещает удаления истории или уже сформированных наборов: отзыв действует на будущее, история выдач остаётся в аудите, у записанных вердиктов сохраняется признак согласия на момент записи. `active=false, consent=null` — нормальное состояние «не выдавалось»; отозванная запись показывается с датами выдачи и отзыва. Имена авторов владелец видит через список участников, остальные — нейтральную подпись. После любого ответа статус перечитывается; `403` дополнительно перечитывает сессию, чтобы интерфейс перестал предлагать команду при потере права. Панель вердикта в карточке риска ссылается на этот экран, когда согласие не дано.

## Администрирование платформы

`/admin` (блок 16, макеты 26–28) — отдельный layout с собственной оболочкой (`widgets/admin-shell`) и отдельным кешем: ключи начинаются с `admin`, заголовок `X-Tenant-ID` не отправляется, смена организации эти данные не трогает. Право проверяется запросом `GET /admin/me` при входе (`AdminLayout`): без права показывается нейтральный экран и ни один admin-запрос не выполняется; роль в организации права не даёт. Ссылка «Администрирование» в оболочках появляется только по признаку сервера. Потеря права во время работы (`403` у команды) перечитывает признак и закрывает оболочку.

Read-экраны (`entities/admin`, `pages/admin`) показывают только метаданные контракта: идентификаторы с сокращением и копированием, статусы с подписями (неизвестные — как есть), время загрузки снимка и ручное обновление без фонового опроса. Списки ограничены лимитом контракта (50/100/200) без выдуманной курсорной пагинации; фильтры живут в адресе и проверяются (перечисления, UUID). Значения семантических фактов сериализуются в JSON с ограничением длины и выводятся текстом; текста сообщений, промптов и сырого вывода модели в контракте нет намеренно, интерфейс их не запрашивает.

Команды (`features/admin/*`): выдача и отзыв права администратора (`201`/`200` различаются, отзыв собственного права предупреждает о закрытии раздела), одиночные `retry`/`replay`/`discard` над мёртвыми заданиями, событиями outbox, AI-заданиями и доставками. Команда предлагается только объекту в статусе `DEAD` без признака «отложено»; перед выполнением диалог называет тип, идентификатор, организацию и операцию. Оптимистичного удаления нет: после любого ответа перечитываются очередь, мёртвые письма и список объекта; `409` объясняется как изменившееся состояние, массовых операций нет. Отчёт о потреблении берёт окно календарных дат UTC (по умолчанию 30 дней, не более 366). Трассировка сообщения различает отсутствующий сегмент («Нет») и ошибку запроса.

## Наблюдаемость

`shared/observability` записывает телеметрию уровня операций: сбои API (метод, шаблон пути с идентификаторами, заменёнными на `{id}`, без query, HTTP-статус, безопасный код из фиксированного алфавита, `traceId`, класс попытки — сеть, таймаут, клиент, доступ, конфликт, сервер) и длительность навигации по шаблону маршрута (`/risks/:riskId`). Тела запросов, заголовки, ключи идемпотентности, тексты и персональные данные недоступны функциям записи по построению. Записи копятся в ограниченном буфере; приёмник подключает слой `app`: адрес из `VITE_TELEMETRY_ENDPOINT` — через `sendBeacon` без cookie, в разработке — консоль, иначе ничего. Кеш запросов ограничен по времени хранения (десять минут без наблюдателей), очищается при выходе и потере сессии; поток сигналов держит одно соединение на организацию с ограниченным backoff и паузой в скрытой вкладке.

## Интерфейс

`shared/ui` — примитивы без бизнес-правил: `UiButton`, `UiField`/`UiInput`/`UiPasswordInput`/`UiSelect` (связка подписи, описания и ошибки через `aria-describedby`), `UiAlert`, `UiErrorState` (подпись по коду + технические детали), `UiDialog` (Reka UI), `UiEmptyState`, `UiSkeleton`, `UiAccessDenied`, `UiIcon` (контуры Material Symbols в `icons.ts`), `UiRingChart` (концентрические кольца; геометрия — `shared/lib/rings.ts`, цвета колец — `RING_TONES`, выведены из токенов палитры). Дизайн-токены объявлены в `src/app/styles/main.css` через `@theme`; динамические строки классов вида `bg-${color}` не используются. Формы — vee-validate с valibot-схемами, локально проверяются только очевидные ограничения контракта, окончательное решение принимает сервер.

## Как добавлять блок

1. Типы — из `Schema<'…'>` (`@/shared/api`), запросы — в `entities/<домен>/api` через `apiClient` + `unwrap`, ключи через `tenantScope`.
2. Пользовательское действие — `features/<глагол-существительное>`: `useRiskCommand` для идемпотентных на сервере команд, `useIdempotentMutation` для append-only записей с ключом; ошибки `ApiError` показываются по коду рядом с командой.
3. Составной блок — `widgets/`, страница — `pages/` + маршрут в `app/router/routes.ts` с `meta.access` и `meta.permission`.
4. Тесты: адаптеры и схемы — unit; транспорт — с подменённым `fetch`; сценарий — Playwright с мок-API (`tests/e2e/fixtures/api.ts`).
