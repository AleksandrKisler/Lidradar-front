# Подготовка реализации US-M01-01 · `flow=invite`

Дата: 29.10.2026. Статус: **черновые технические заметки; пять desktop-макетов согласованы, следующим идёт обновление US**. Это предварительный материал для будущего задания, а не готовое поручение на реализацию. По [правилу изменения US](../USER-STORY-CHANGE-WORKFLOW.md) решение и границы завершаются после обновления канонической US. Runtime-код, ENV, OpenAPI и БД не менялись; согласованные макеты и ссылки на них перечислены в журнале дизайна. Реализация и функциональная приёмка ещё не выполнены.

Основной документ: [сценарий, тексты и критерии приёмки](./us-m01-01-invitation-entry.md).

## Решение и границы

- Одна `RegisterPage`, маршрут `/register` остаётся существующим гостевым маршрутом.
- «Создать аккаунт» → `/register`; «У меня есть приглашение» → `/register?flow=invite`.
- Режим читается из существующего `GET /api/v1/auth/registration`. Серверный `LIDRADAR_REGISTRATION_MODE` принимает `open` / `invite_only`; новый frontend ENV не вводится.
- `flow=invite` → проверка кода → данные аккаунта на той же странице; в `open` обычный путь сразу открывает данные; в `invite_only` обычный путь показывает warning над карточкой, отключённые поля и кнопку, активный переход к приглашению.
- Успех предварительной проверки не резервирует и не расходует код. `POST /auth/register` сохраняет `inviteCode` в теле и повторно проверяет его.
- Приглашения платформы и сотрудников сохраняют действующие последствия. Авторизованный `/invitations/accept` не используется для гостевой проверки.
- В рамках этого изменения не вводятся привязка к email, новые способы выдачи кодов, изменение сроков приглашений, новый механизм сессий или автоматическое открытие по календарю.

Согласованные требования отделены в спецификации от предложенных настроек: задержка 400 мс, клиентский TTL 30 минут и 10 проверок за 15 минут на IP. Дату открытия не назначаем; 15 января 2027 года пока является трактовкой исходного пожелания.

### 5. Backend и контракт

Предлагаемый метод: `POST /api/v1/auth/registration/invitation/check`, JSON `{ "code": "<43 символа>" }`.

| Ответ                    | Смысл                                                    |
| ------------------------ | -------------------------------------------------------- |
| `204`                    | Код можно использовать сейчас; тело и cookie отсутствуют |
| `400 INVALID_ARGUMENT`   | Пустой код, неподходящий JSON/тип, некорректное тело     |
| `403 INVITATION_INVALID` | Непустой код непригоден, без раскрытия причины           |
| `429`                    | Действующее ограничение, положительный `Retry-After`     |
| `5xx`                    | Сбой проверки; не приравнивается к негодному коду        |

В запросе нет `X-Tenant-ID`, в ответе нет идентификаторов организации, роли или типа приглашения. Все ответы `Cache-Control: no-store`. Проверка возможна в обоих режимах; правила окончательной регистрации не меняются.

Обёртка над `admit` сначала проверяет непустой код, использует действующий IP limiter с новым scope и существующий источник времени. Не вызывает `Register`, хеширование пароля, приём приглашения, создание сессии или отправку письма. Проверить применимость ограничений scope в схеме rate limiter; не обещать отсутствие миграции до этой проверки.

Затрагиваемые backend-файлы: `backend/internal/identity/application/service.go`, `rate_limit.go`, `transport/http_handler.go`, их тесты, `backend/internal/integration/invitation_registration_test.go`, `contracts/openapi/openapi.yaml`. Использовать существующие интерфейсы чтения `PlatformInvitationUsable` и `CheckMemberInvitation`.

До изменения backend прочитать обязательные документы из его `AGENTS.md`. Обновить решение ADR 0057 по правилам governance (если нужен отдельный ADR — оформить и принять до архитектурных изменений), описание API и US-M01-01/02 и сценарий регистрации сотрудника. Сохранить атомарность/компенсацию существующей регистрации.

Готовность этапа: серверные тесты подтверждают положительный ответ без расходования и побочных эффектов, общий ответ на негодные коды, независимость лимитов и успешную последующую регистрацию. ### 6. Frontend

Оставить существующий маршрут и `AuthLayout`. Предлагаемое размещение: модель `use-registration-flow.ts` и адаптер временного контекста внутри `src/features/auth-session/model/`, компонент `InvitationCodeForm.vue` внутри того же feature. Использовать публичные экспорты feature и entity.

`RegisterPage` разрешает начальный сценарий; модель хранит переходы и контекст; `InvitationCodeForm` отвечает за ввод и единый путь автоматической/ручной проверки; `RegisterForm` — за данные аккаунта. Отдельный маршрут и новый глобальный store не требуются. Код не помещается в query keys или общий кеш запросов; прерываемая проверка — явная команда без автоматических сетевых повторов.

Порядок начального разрешения:

1. Извлечь код из новой или старой ссылки, удалить его из адреса через `replace`, установить `flow=invite`. Не отправлять аналитику с исходным кодом. Смена URL для очистки не должна запускать второй запрос.
2. Новый код имеет приоритет над сохранённым; некорректная ссылка показывает ошибку и ручной ввод, даже при `open`.
3. Без кода определить точное `flow=invite`; для него восстановить допустимый контекст и перепроверить его либо показать пустое поле.
4. Для обычного входа прочитать серверный режим: загрузка/ошибка с повтором → закрытое состояние либо обычная форма. Сохранённое приглашение в обычный путь не переносить.

Критические переходы: одна отправка при гонке debounce/Enter/кнопки; отмена при смене сценария; восстановление после обновления; очистка после успеха; TTL; запросы из двух вкладок; серверный отказ после успешного precheck; `INVITATION_REQUIRED` при устаревшем `open`. Сохранять только имя/почту в памяти при возврате к коду; пароль не переносить между шагами.

После подтверждённого `201` отметить аккаунт созданным и очистить приглашение до загрузки `/auth/me`. Сбой чтения сессии показывает повтор её загрузки; создание аккаунта не повторяется. Неизвестный результат самого POST регистрации обрабатывается существующей политикой ошибок, без автоматической повторной регистрации.

Ключевые изменения: `LoginPage.vue`, `RegisterPage.vue`, `RegisterForm.vue`, `schemas.ts`, `auth-session/index.ts`, `registration-api.ts`, `entities/session/index.ts`; новые модель/контекст/форма внутри auth-session. `routes.ts` и общий guard менять только при выявленной необходимости: query уже поддержан существующим маршрутом. Соседние настройки, онбординг и компоненты UI не входят в пакет.
