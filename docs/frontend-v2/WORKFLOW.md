# Работа над frontend v2

До релиза 01.11.2026 действует [фиксация макетов](DESIGN-FREEZE.md) от 30.10:
Доступ/Онбординг без правок, Radar без крупных изменений. В этих областях она
имеет приоритет над прежними планами дизайн-правок и шагом «макеты» ниже.
Реализацию и QA продолжать по зафиксированным эталонам.

Для исправлений и расширений US, выявленных пользователем, действует
[порядок изменения user stories](../USER-STORY-CHANGE-WORKFLOW.md) от 29.10.2026:
макеты → согласование пользователем → обновление US → решение и границы →
backend → frontend → тестирование изменённой и связанных US. Этот порядок
имеет приоритет над циклом реализации ниже для таких изменений. Существующие
ограничения релиза и распределение исполнителей сохраняются; новый пакет
поставки определяется на этапе решения и границ.

Workflow применяется к выбранному исполнителю: Claude или Codex. По поручению
владельца 29.10.2026 Codex также может продолжать реализацию и исправлять runtime
после Claude; прежнее ограничение «Codex только принимает» отменено. Перед сменой
исполнителя передавай snapshot/findings и владение файлами, сохраняя dirty tree.
Не запускай двух авторов на общих файлах. Вход Codex: [AGENTS.md](../../AGENTS.md),
[запуск](CODEX.md) и [правила ролей](CODEX-OPERATING-RULES.md).

Уточнение владельца 29.10.2026: для текущих US-M01-01/02 и обычной дальнейшей
работы действует схема трёх участников ([Claude](CLAUDE-OPERATING-RULES.md),
[Codex](CODEX-OPERATING-RULES.md)): основная сессия выбранного исполнителя
пишет код; `lidradar-qa` тестирует, затем функционально
принимает; после его PASS `lidradar-visual-review` принимает desktop/tablet/mobile.
Opus у Claude / Astra у Codex — ограниченная консультация по явному вопросу. Шестиролевые
конфигурации сохранены как LEGACY и не запускаются по умолчанию.

ТЗ US-M01-02 согласовано; запуск Claude ранее отложен. Подготовка структуры Codex
сама по себе не запускает frontend. [Продолжение доступа](ACCESS-RESUME.md)
начинается с инвентаризации существующего snapshot/findings, не с повторного
написания A/B/C. Живое QA — локальный frontend dev:stage с актуальным
backend-stage; отсутствие локального backend не блокирует. Unit/mock и
живые доказательства разделяются. У общих файлов один автор записи.

Перед реализацией читать [RELEASE-SCOPE.md](RELEASE-SCOPE.md): текущий релиз
ограничен стабильным API. Новые backend-возможности отложены; неподдержанные
US-шаги получают явное соответствие доступному пути либо статус «отложено».
API-ограничения не являются причиной останавливать независимые frontend-сценарии.

## Цикл этапа

1. Сверь `git status`, текущую ветку и чужие правки. Для реализации создай отдельную
   ветку `frontend/v2-implementation`, если её нет; не сбрасывай и не перезаписывай
   существующую. Если ветка уже занята другой работой, выбери свободную с суффиксом.
   Подготовленная конфигурация может быть ещё не закоммичена: сохрани её.
2. Создай компактный task brief: цель, story IDs/шаги, nodes, API, состояния,
   allowed files, общие владельцы, проверки и acceptance. Никаких часов чтения всего.
3. Получи Figma evidence. Начни с существующих primitives и sibling workflow.
4. Реализуй вместе визуал, данные, состояния и значимые тесты.
5. Выполни проверки и запиши команды/exit code/версию изменений. Подготовь скриншоты.
6. На замороженном diff QA завершает TEST, затем FUNCTIONAL review; только после
   обоих PASS запускается UI-review всех трёх размеров. Пока review использует
   снимок, основной разработчик код не меняет. Reviewer сообщает findings, не правит.
7. Исправь подтверждённое; повтори затронутые проверки/review. После двух неудачных
   исправлений одной причины прекрати повторение гипотез и собери диагностику;
   отдельная ограниченная консультация Opus/Astra не запускается автоматически.
8. Обнови STATUS и evidence. PASS допустим только для реально проверенного объёма.
   Не останавливайся на очередном плане, если реализация уже разрешена.

## Команды и частота

- Используй Node 24.19.0 из `.nvmrc`; launcher выбирает установленную версию.
- Baseline F00: `npm run check`, `npm run build:pre-prod`, адресный Chromium smoke.
  Зафиксируй существующие сбои отдельно от внесённых. Сбой остаётся сбоем.
- Во время правок: адресные `npm run test:unit -- <paths>` и
  `npm run typecheck`; lint затронутых файлов, когда нужно.
- Конец сценария: `npm run check`, `npm run build:pre-prod`, адресные Playwright
  E2E с `--project=chromium` и применимая responsive/a11y матрица.
- После изменения общих компонентов: smoke всех их ключевых потребителей,
  не только страницы пилота. Не запускать одновременно Playwright suites,
  использующие один preview server/порт.
- Перед финальной приёмкой: `npm run check`, три существующие build команды
  dev/pre-prod/prod, `npm run audit:release`, `npm run test:e2e` для штатной
  browser-матрицы CI. Стендовые сценарии запускать отдельно только с разрешённой
  средой; реальные побочные эффекты не разрешаются автоматически этим документом.
- Если Playwright browsers отсутствуют, установи необходимые browser binaries;
  не меняй browser coverage для обхода ошибки. Существующий CI не ослаблять.

## Визуальная проверка

У каждого кадра есть Figma node, viewport, fixture, locale/timezone, browser/version,
device scale factor, font readiness и состояние. Заморозь время/данные/анимации;
дождись `document.fonts.ready`, загрузки assets и целевого состояния без arbitrary sleeps.
Desktop берётся из frame; базовые tablet 834×1194 и phone 390×844. Проверяй
также существующую узкую/промежуточную матрицу и длинные реальные по форме данные.
Высота длинного full-feed frame не равна высоте viewport.

Первый browser baseline сверяется с Figma визуально, overlay/diff и измерением
геометрии. После принятия добавляются Playwright screenshot assertions в стабильной
среде; cross-browser typography может отличаться. Не вводи произвольный общий
процент pixel diff как доказательство качества. Допуски обосновываются на пилоте.
Не маскируй layout/контент; допустимые динамические области перечисли явно.
Тесты должны ловить изменения approved browser baseline, а не обновлять его молча.

## Экономия

Одна основная сессия пишет код и координирует; один QA, один UI. У Claude это
Sonnet; распределение моделей Codex задано в CODEX-OPERATING-RULES.
Opus/Astra только для ограниченной явной консультации. В Codex независимые
задачи можно передать worker/explorer с отдельным write set; в штатной приёмке
они не добавляют дублирующих проверок. Тестовые
команды выполняет QA; UI читает готовые изображения. Не плодить агентов
для повторного чтения контракта и не запускать все полные suites после каждого
малого исправления: адресное воспроизведение → затронутые проверки → финальный gate.
Контекст агента — task brief, relevant files, diff, evidence; не вся история.
Сохраняй короткие выводы вместо полных логов. Кэшируй неизменные Figma exports.
`maxTurns` в Claude ограничивает один вызов, не весь бюджет; partial → UNVERIFIED.
Проверяй доступную статистику расхода клиента, фиксируй расход пилота, не обещай
неизмеренную экономию. После приёмки этапа сохраняй handoff и освобождай контекст.

## Формат отчёта

Статус; story IDs и проверенные шаги; список файлов; Figma nodes;
команды + exit codes + revision; actual/reference/diff screenshot paths;
review verdicts; остаточные проблемы; следующий шаг.
Разделяй mock/frontend проверку, реальный backend/worker и пользовательскую приёмку.
