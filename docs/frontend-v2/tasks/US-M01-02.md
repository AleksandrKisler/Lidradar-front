## 3. API и фактический backend

Backend с ADR 0067/0068: `0d06d96b62b03947e6cda10615c8c57324a479f4`.
SHA-256 OpenAPI:
`9f9766cc4d23e398268aabc68d8adae6db9bf3358bf14953b151f36c617e3027`.
Локальный API/DB/race-прогон и независимое ревью выполнены ранее:
`Lidradar/docs/engineering/evidence/2026-10-29/us-m01-02/backend-verification.md`.
Этот отчёт не доказывает поставку API на стенд, UI или внешнюю доставку почты.

Новых методов, лимитов, миграций или ENV у US-M01-02 нет.
`POST /api/v1/auth/register`, существующий request:
`{ displayName, email, password, inviteCode? }`. В A `inviteCode` отсутствует,
в B — из проверенного контекста; окончательное решение всегда за сервером.

| Ответ / событие                                       | Действие frontend                                                                                                 |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `201`, user + session cookie                          | Зафиксировать `account-created` до `/auth/me`, очистить контекст приглашения; штатные guards                      |
| `400 REGISTRATION_FAILED`                             | Подтверждённый отказ; один нейтральный блок над полями, данные и B сохранены                                      |
| Legacy `409 EMAIL_ALREADY_REGISTERED`                 | Тот же блок и поведение совместимости, без раскрытия причины в UI                                                 |
| `400 INVALID_ARGUMENT` и прочие коды `400/409`        | Не классифицировать по одному HTTP-статусу как подтверждённый нейтральный отказ                                   |
| `403 INVITATION_REQUIRED`                             | Переход/перечитывание режима по US-M01-01; не подменять общей ошибкой этой US                                     |
| `403 INVITATION_INVALID`                              | Базовый переход B3 → B2, красный !, сброс подтверждения/пароля; имя/email допустимо оставить в памяти             |
| `429 RATE_LIMITED`                                    | Прежний register Retry-After, изменение email не снимает отсчёт, автоматического POST после ожидания нет          |
| Потеря ответа, timeout, неразбираемый ответ или `5xx` | Возможен неизвестный исход; сверка `/auth/me`, без автоматического повторного POST и обещания «аккаунт не создан» |
| Ошибка `/auth/me` после полученного `201`             | Аккаунт уже создан; повторять только загрузку сессии                                                              |

Новый конверт отказа содержит `error.code`, нейтральный server `message` и
`traceId`, без `details` и `Set-Cookie`. UI не выводит raw message/code,
email-причину или trace ID третьей строкой этого бизнес-блока.
Оба известных кода распознавать адресно, не все `400/409` подряд.

`201`/сессия и отказ остаются различимы. Пакет убирает явное раскрывающее
сообщение, но не вводит полную неразличимость регистрации, email-first/OTP,
CAPTCHA, проверку доступности email или идемпотентность существующего POST.

Если frontend-контракт уже синхронизирован US-M01-01, сверить provenance/hash
и переиспользовать его. Иначе штатные `api:sync`, `api:generate`, `api:check`
из выбранной чистой копии backend. Не перезаписывать чужой dirty контракт
и не редактировать generated вручную. Backend и серверный контракт — чтение.

## 4. Пользовательский путь и состояния

| Вариант          | Путь                                                                                                                                       |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| B, основной      | Login → B2/precheck → B3/данные → общий отказ → исправление только email → один успешный POST → организация/онбординг и независимое письмо |
| A, только `open` | Обычный `/register` без кода → общий отказ → исправление email → успешная регистрация, онбординг и независимое письмо                      |
| C, регрессия     | Отключённая форма с warning не отправляет POST и не получает состояние ошибки отправки; активный переход к B сохраняется                   |

Занятый адрес — известное тестовое предусловие, а не сообщение интерфейса.
После подтверждённого отказа над полями один `UiAlert tone=danger`:

> Не удалось создать аккаунт
>
> Проверьте данные или попробуйте позже.

Не назначать email ошибку занятости или специальное выделение. Постоянная
ссылка «Уже есть аккаунт? Войти» сохраняется в обычном месте, не появляется
в зависимости от ответа. Автоматического входа/восстановления после отказа нет.

| Состояние                      | Данные и действия                                                                                                               |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| Ready A/B3                     | Имя/email/password, соответствующие пояснение и ссылка A или B; видимого поля кода нет                                          |
| Submitting                     | Один POST, поля/повтор недоступны; «Создаём аккаунт…», индикатор, значения сохранены                                            |
| Registration rejected          | Форма разблокирована, нейтральный блок; имя/email/скрытый password в памяти сохранены, B остаётся проверенным                   |
| Editing after rejection        | Изменение поля очищает устаревший общий блок; остальные значения и B остаются; сетевых запросов на ввод нет                     |
| Explicit retry                 | Кнопка/Enter отправляют актуальный email, прежние остальные данные и тот же ещё действующий inviteCode B                        |
| Local validation error         | Неверный email — «Введите корректный адрес электронной почты.» у поля; POST не уходит. Общий отказ не заменяет форматную ошибку |
| Rate limited / unknown outcome | Редактирование email не снимает соответствующую блокировку; отдельная обработка базовой модели                                  |
| Success / session recovery     | После `201` повтор POST невозможен; загрузка `/me` и существующий дальнейший путь                                               |

Фокус после общего отказа — в локальную программно фокусируемую обёртку
сообщения (`tabindex=-1`) после обновления DOM и разблокировки формы.
`UiAlert` сохраняет `role=alert`; фокус виден, ошибка относится к форме.
Локальные ошибки сохраняют `focusFirstProblem`, label/description/invalid
соответствующего поля. Общий helper фокуса ради этой ветки не менять.

Пароль хранится только в памяти текущей формы, отображается скрытым;
не переносится в storage/URL/query cache/telemetry, F5 и другие сценарии.
Подтверждённый отказ не очищает и не продлевает 30-минутный контекст B.
Уход, выход, другое приглашение, TTL, F5 с серверной перепроверкой и
финальный отказ кода сохраняют правила US-M01-01/ADR 0067.
При истечении/отзыве/чужом использовании кода между отказом и повтором
действует финальная серверная проверка, а не прежний precheck.

После успеха новый клиент с серверным разрешением идёт в шаг компании;
сотрудник — в организацию владельца. На отказе нет перехода в онбординг/Radar
или нового входа. Frontend не отправляет дополнительное письмо после POST
и не ждёт доставки для перехода. Получатель письма успеха — исправленный email.
Серверные инварианты «нет нового user/session/организации/письма на отказе»
подтверждаются API/серверными доказательствами, не одним mock UI.

## 8. Проверки, evidence и завершение

Матрица содержит все 10 AC, адресные общие критерии US-M01-01, регрессии,
API/compatibility, a11y и три устройства. QA сначала запускает проверки, затем отдельно читает код и принимает
полноту/смысл доказательств. Два этапа различаются в отчёте; зелёный тест
и слово автора не заменяют приёмку AC.

Планируемые отчёты: `docs/frontend-v2/evidence/US-M01-02/` — manifest,
source-map, test-report, QA test/functional и UI desktop/tablet/mobile verdicts, handoff.
Изображения: `artifacts/frontend-v2/us-m01-02/<snapshot>/`.
Manifest: frontend HEAD плюс hash содержимого изменённых/новых файлов,
исходный dirty baseline, backend SHA/API hash, test/capture inputs, команды
и exit codes, fixture IDs, mode/type приглашения, node/reference-kind,
viewport/scale, browser/version, locale/timezone/fonts и пути evidence.
Один HEAD при dirty tree не определяет проверенную версию.
Пароли, действующие приглашения и cookie не включать в отчёты/трейсы;
визуальные фикстуры синтетические. Не трогать evidence US-M01-01.

Вердикт: `PASS | FAIL | BLOCKED | UNVERIFIED`, snapshot, фактический объём,
просмотренные изображения/логи; finding с ID/severity/AC, file:line или
node/state/viewport, trigger, expected/actual, evidence и проверкой исправления.
Недостающие проверки/нечитаемые изображения — не PASS. Старые baseline-сбои
фиксируются отдельно; thresholds/CI/baselines не ослабляются ради зелёного gate.

Предъявление результата владельцу: QA TEST/FUNCTIONAL PASS и UI PASS трёх размеров на одной версии,
все обязательные AC проверены, нет открытых дефектов/обязательных UNVERIFIED,
