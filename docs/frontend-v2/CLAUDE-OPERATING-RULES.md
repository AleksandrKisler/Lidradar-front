# Claude · Модели, экономия контекста и среда frontend

Дата: 29.10.2026. **Accepted**: владелец выбрал «3 участника: разработчик +
QA + UI». Ниже действующая схема: основная сессия и два субагента, все Sonnet.
Эти правила не разрешают запуск frontend или агентов: пользователь пока
разрешил подготовку/коммит документов и обновление backend-stage.

## 1. Действующие уточнения

- Основная модель — **Sonnet**. Код, тесты и обычная приёмка — Sonnet;
  в штатных конфигурациях US-M01-01/02 указан `model: sonnet`, а не наследование
  случайно выбранной дорогой модели родительской сессии.
- **Opus только консультирует** по ограниченному архитектурному/контрактному
  вопросу: симптом, relevant diff, контракт, что уже проверено, один вопрос.
  Он не пишет код, не запускает тесты/агентов и не читает весь проект.
  Два неудачных исправления — повод остановить повторение гипотез и собрать
  диагностику, а не автоматический вызов Opus. Консультация запускается явно.
- Отдельный Haiku ради запуска `npm` не нужен: команды выполняются инструментами
  без отдельного LLM-процесса. Если потребуется узкая сортировка больших логов,
  Haiku можно предложить отдельно; функциональную приёмку регистрации на него
  автоматически не переносить. Не добавлять агента только ради использования
  ещё одной модели.
- Действуют три участника: основная сессия Sonnet пишет код, `lidradar-qa`
  тестирует и функционально принимает, `lidradar-visual-review` принимает UI
  всех трёх размеров. Шесть конфигураций каждого прежнего пакета сохранены
  как LEGACY и в обычном запуске не используются. Никаких дополнительных
  менеджеров, Agent Teams и вложенных агентов.
- Модель/настройки фактической сессии проверить перед работой. Не менять
  глобальные credentials/provider, не подключать альтернативный API и не
  считать конфигурацию доказательством фактически использованной модели.

## 2. Среда: frontend локально, backend на stage

Живой пользовательский прогон:
`http://127.0.0.1:5173` → существующий Vite stage-proxy →
`https://stage.app-lid-radar.ru`. Команда frontend: `npm run dev:stage`.
Отсутствие локального backend на 8080/8081 **не блокирует** эту схему.
Не поднимать локальный backend вместо согласованного stage.

`DEV_STAGE_BASIC_AUTH_USER/PASSWORD` читаются сервером Vite из
`.env.stage.local`; не печатать их, не добавлять `VITE_` и не коммитить файл.
Использовать существующую обработку Origin/cookie в stage-proxy, не обходить её
прямым cross-origin fetch из браузера и не ослаблять CSRF/TLS/backend cookie.

Перед живым QA фиксировать stage-gate:

1. Развёрнутый backend revision и версия образов; для ADR0067/0068 целевой
   commit `0d06d96b62b03947e6cda10615c8c57324a479f4` либо проверенный потомок.
2. Миграция `000032_registration_invitation_check`, готовность API,
   доступный precheck и нейтральный ответ регистрации по ADR0068.
3. Фактический серверный OpenAPI hash и соответствие выбранному frontend
   контракту. Для указанного commit:
   `9f9766cc4d23e398268aabc68d8adae6db9bf3358bf14953b151f36c617e3027`.
4. Режим из GET регистрации, работоспособность Basic Auth/proxy и разрешённые
   тестовые данные/почта. Режим нельзя угадывать по `.env` frontend.

Старый stage — блокировка живого QA, а не причина заново писать frontend.
Обновление backend выполняет оператор по отдельному поручению; frontend-агенты
не деплоят backend и не применяют миграции. Не сбрасывать демо-данные,
счётчики лимитов или общий стенд ради теста. Изменение режима A/C — только
согласованное окно/конфигурация stage; неподходящий режим явно ограничивает
соответствующий живой прогон.

Unit/component, mock E2E и детерминированные visual fixtures остаются
локальными. Они проверяют ошибки/гонки/оба режима и не заменяются целиком
живым stage. Stage добавляет интеграционные доказательства, но не делает
mock-тест реальным API-тестом. Сценарии с изменением данных используют
только выделенные synthetic accounts/invites; отправку писем проверять в
разрешённом mail sink/контролируемой тестовой почте. Не использовать production.

## 3. Продолжение без повторного написания

Перед кодом читать [ACCESS-RESUME.md](ACCESS-RESUME.md), актуальный manifest
и список открытых findings. Первое действие — сопоставить требования с
**существующим** кодом/тестами и их hash, а не генерировать новую форму.
US-M01-02 уже пересекается с US-M01-01: одна общая форма и один владелец записи.

Карта продолжения: `AC → есть в коде / проверено на этом snapshot / дефект /
нет evidence / блокировка среды`. Наличие кода не равно PASS, но и отсутствие
отчёта не разрешает переписывать готовую реализацию. Исправлять минимальную
причину конкретного finding; новые schema/store/компоненты не создавать
параллельно существующим. Runtime незакоммичен — сохранить, не reset/stash.

Сначала адресное воспроизведение ошибки и проверки затронутых зависимостей;
полный suite/build/browser-matrix — после устранения известных адресных сбоев
и на финальном снимке. Не повторять без новых оснований уже выполненные команды
для неизменённых inputs. Обязательные финальные gates и coverage сохраняются.
Документальная правка требует проверки документов, а не повторного прогона
всех browser-сценариев; изменение runtime делает прежний результат историческим
до проверки зависимости. Не объявлять старый PASS проверкой нового файла.

Figma exports, node map, synthetic fixtures и reference hashes получать один
раз и переиспользовать. Не выгружать весь Figma-файл и весь репозиторий каждому
агенту. Browser/capture имеет одного владельца; не запускать процессы с одним
портом одновременно. Исполнитель не может «исправить» дефект удалением AC,
ослаблением assertion, budget/coverage или молчаливым обновлением baseline.

## 4. Контекст и отчёты

Главный brief: цель, story/AC, разрешённый diff, нужные файлы/строки, snapshot,
точные evidence paths и список вопросов. Передавать пути, а не всю историю.
Большие логи сохранять в artifacts; в разговор возвращать команды/exit code,
первые релевантные ошибки и ссылку. Следующую часть читать по необходимости.
Не переисследовать неизменные решения/ADR на каждой итерации.

После осмысленного этапа сохранять короткий handoff: что сделано, что прошло
на какой версии, что не прошло, следующий конкретный шаг. При исчерпании лимита
новая сессия начинает с handoff, не с повторного построения архитектуры.
Фиксировать доступную статистику расхода по модели/роли на пилоте; не обещать
процент экономии без измерений и не считать деньги API эквивалентом остатка
подписочного лимита. Недостаточный бюджет не превращается в PASS.

Основание настройки моделей и контекста: официальные
[subagents](https://code.claude.com/docs/en/sub-agents) и
[cost management](https://code.claude.com/docs/en/costs), просмотрены 29.10.2026.
Отдельные агенты делают собственные запросы; каждый получает отдельный контекст.
Сокращение дублирующего чтения — проектное решение, конкретная экономия пока не измерена.

## 5. Действующий обычный цикл из трёх участников

**Accepted 29.10.2026**, заменяет шестиролевой запуск US-M01-01/02.
Продуктовые AC и требования доказательств сохраняются; запуск пока отложен.

| Участник                                    | Модель | Работа                                                                                                            |
| ------------------------------------------- | ------ | ----------------------------------------------------------------------------------------------------------------- |
| Основная сессия: разработчик и координация  | Sonnet | Инвентаризация текущего состояния, код и тесты, исправления, handoff                                              |
| Независимый QA + функциональный принимающий | Sonnet | Сначала выполнить тесты, затем отдельно проверить AC/API/пограничные случаи и код; исходники не правит            |
| Один визуальный принимающий                 | Sonnet | Последовательно desktop/tablet/mobile; три отдельных результата на одном snapshot, без трёх одинаковых контекстов |
| Консультант по доказанной сложной проблеме  | Opus   | Короткая консультация по запросу, в обычном цикле отсутствует                                                     |

Это **два субагента плюс основная сессия**, а не шесть субагентов плюс
отдельный менеджер. Фазы сохраняются: текущее состояние/готовность stage →
код → тестирование → функциональная и UI-приёмка → исправления с повторной
проверкой затронутого. QA независим от автора, но запуск тестов и оценка их
смысла не требуют двух агентов с одинаковым набором файлов.

Слабые места исходной схемы: повторное чтение одного контракта шестью
контекстами; две похожие функциональные роли; три UI-агента повторяют базовую
типографику/форму; широкие повторные прогоны превращают одни и те же ошибки
в большие логи. Разные viewport сами по себе не создают независимую экспертизу.
Больше агентов не гарантирует больше покрытых AC.

Риск сокращения: один UI-агент может пропустить различие breakpoint, QA может
слишком довериться зелёным тестам. Поэтому остаются отдельный чек-лист каждого
устройства, реальные изображения/измерения и явный AC-review после тестов.
Для крупной перестройки общего layout можно отдельно разнести UI-проверки;
для контрактной/авторизационной неоднозначности — отдельная консультация.
Не компенсировать экономию ослаблением проверок безопасности или адаптивов.

Владелец принял эту схему для дальнейшей обычной работы и текущих US-M01-01/02.
Шесть узких конфигураций остаются историческими документами; вернуть их
в активный запуск можно только отдельным решением. Новое распределение ролей
не является разрешением frontend-реализации или автоматического запуска Claude.
