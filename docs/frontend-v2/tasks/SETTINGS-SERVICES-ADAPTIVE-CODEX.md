## Контракт и данные

Используй существующие `src/entities/service` и `src/features/manage-services`:
GET/POST `/api/v1/services`, PATCH/DELETE `/api/v1/services/{serviceId}` с
`X-Tenant-ID`. DELETE — мягкое отключение, PATCH `{ active: true }` — включение.
Права чтения/изменения `service.manage`, каталог владельца; менеджеру управление
и прямой URL не становятся доступны из-за редизайна. Generated/API/backend не менять.

Сохрани нормализацию имени, текущие ограничения Unicode-длины, точку или null
для всей организации, валюту и десятичные строки цен. Используй `parseAmount`,
`formatPriceRange`, `serviceSchema`; не добавляй параллельное форматирование денег.
Точная цена, диапазон, только «от», только «до», обе границы null и копейки
имеют разные представления. Неизвестная цена — «Не указана»; не вычисляй
среднее, не превращай её в 0 и не конвертируй валюту.

Для visual fixture воспроизведи шесть примеров эталона: `31 000 ₽`,
`8 000–12 000 ₽`, `от 1 500 ₽`, `до 3 500 ₽`, `Не указана`, `1 490,50 ₽`;
пять активных и одна отключённая услуга, счётчики 6/5/1. В runtime фильтры,
счётчики и «Показано … услуг» должны соответствовать фактическим данным.
Ошибки форм: пустое имя, неверный диапазон, отрицательная/нечисловая/нулевая
цена; копейки разрешены. Нормализованная payload и число запросов проверяются
отдельно от подписей UI.

Проверь двойной submit до/после async validation, refresh при dirty-форме,
закрытие/повторное открытие, смену услуги, tenant и уход со страницы во время
команды. Зафиксируй tenant/ID команды; поздний ответ A не должен закрывать
диалог B, менять его поля или подтверждать сохранение в B. Unknown network
outcome не называй success и не превращай в автоматический повтор POST.
Изменения управления UI-состояниями допустимы в рамках стабильного API.
