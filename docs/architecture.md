# Архитектура FSD

Направление зависимостей: `app → pages → widgets → features → entities → shared`.

Модуль может импортировать нижние слои, но не верхние. Слайсы одного слоя независимы друг от друга. `app` и `shared` не имеют бизнес-слайсов: они делятся на технические сегменты. `processes` не создаётся: этот слой устарел в актуальной FSD.

## Пример из проекта

`pages/radar` компонует `widgets/risk-workspace`. Виджет загружает `entities/risk` и отображает действие `features/acknowledge-risk`. Фича использует сущность, общую кнопку и Reka Dialog. Сущность валидирует серверный ответ через Zod. Shared API ничего не знает о рисках.

В каждом слайсе есть `index.ts` с явными экспортами. Не экспортируйте всё через `export *`, не делайте единый `src/index.ts` и не импортируйте чужие внутренности:

```ts
// Правильно: публичный контракт слайса.
import { getRisk } from '@/entities/risk'
// Внутри entities/risk/api — относительный импорт собственной модели.
import { riskSchema } from '../model/risk'
```

`npm run lint:fsd` запускает официальный архитектурный линтер Steiger с рекомендуемыми правилами. Правила не заменяют ревью: следите за смыслом слайсов и не превращайте shared в хранилище всего подряд.

## Добавление функциональности

1. Создайте доменную сущность в `entities/<domain>` с `model/`, `api/`, при необходимости `ui/`.
2. Пользовательский сценарий поместите в `features/<verb-noun>`.
3. Самостоятельный блок страницы — в `widgets/`; простую композицию можно оставить прямо в `pages/`.
4. Экспортируйте только необходимое через `index.ts`.
5. Добавьте маршрут в `app/router/index.ts` и пользовательские тесты.

Не нужно создавать все сегменты заранее: добавляйте `lib/`, `api/`, `model/`, `ui/` по фактической потребности. Пустой `shared/lib` задокументированы как точки расширения.

## Состояние

В примере состояние локально у виджета. Pinia намеренно не добавлена без сценария общего состояния. Если она понадобится, настройте `createPinia()` в app, размещайте stores внутри соответствующих entities/features, а не в глобальной папке stores. Состояние сервера и клиентские предпочтения стоит разделять; при сложном API можно добавить TanStack Vue Query.

## UI

Reka UI отвечает за поведение диалога: клавиатура, фокус, ARIA и портал. Tailwind — за оформление. Нативная кнопка обёрнута в `shared/ui/UiButton.vue`; простому button не требуется отдельный headless-компонент. Составной бизнес-диалог остаётся внутри features, пока нет реального повторного использования.

Темизация — в app/styles/main.css. Не используйте динамические строки вида `bg-${color}-500`: Tailwind не сможет статически обнаружить их; применяйте словарь полных классов.

Правило `fsd/insignificant-slice` отключено для шаблона: feature/widget оставлены как пример разделения даже при единственном использовании. Проверки запрещённых импортов и public API включены. При развитии проекта пересмотрите это исключение.

Локальное ESLint-правило в `tooling/eslint/fsd.mjs` дополняет Steiger для import, dynamic import и re-export, включая относительные пути. Проверяется командами `npm run lint` и `npm run test:architecture`. Используйте статические пути и единственный alias `@/`; при добавлении новых aliases расширьте resolver правила.
