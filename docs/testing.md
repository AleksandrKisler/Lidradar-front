```sh
npm run check
npx playwright install
npm run test:e2e
```

E2E сам собирает pre-prod и поднимает preview на 4173. `E2E_BASE_URL=https://… npm run test:e2e` отключает локальный сервер, но моки маршрутов остаются.

Набор на учебном стенде — `tests/e2e/stand/` (профиль Playwright `stand`, `npm run test:stand`): три учебных пользователя `empty`, `small` и `large` из runbook backend, вход каждым по API, только чтение. Он пропускается, пока не заданы путь к файлу с паролем стенда и адрес dev-сервера, который проксирует `/api`:

```sh
LIDRADAR_STAND_PASSWORD_FILE=../Lidradar/runtime/frontend/password.txt \
E2E_BASE_URL=http://127.0.0.1:5173 npm run test:stand
```

Профиль `stand` не делает повторов и не пишет трассы, видео и снимки при падении: в них могли бы оказаться cookie сессии и содержимое переписок. Ожидания строятся на инвариантах фикстур и снимках API, а не на числах из макетов; `large` проверяет курсорные списки без дублей и отсутствие N+1 по сети. Данные стенда восстанавливаются командами `make frontend-data-down` и `make frontend-data-up` из репозитория backend. Менеджера и администратора платформы на стенде нет — эти роли проверяются на мок-API.

Матрица reflow и доступности — `tests/e2e/responsive.spec.ts` (только Chromium): ключевые маршруты на ширинах 320, 375, 768, 1024, 1440 и имитация 200 % масштаба; на каждой — отсутствие горизонтальной прокрутки страницы, доступное главное действие, axe без нарушений и видимый фокус после первого Tab, плюс уважение к `prefers-reduced-motion`.

Аудит выпуска — `npm run audit:release`: production-сборка, затем `scripts/release-audit.mjs` проверяет отсутствие карт исходников и адресов разработки в артефактах, совместимость `index.html` с CSP без inline-скриптов, отсутствие строк, похожих на секреты, бюджеты сборки из `bundle-budgets.json` (базовые значения плюс 20 %; чанки администрирования не входят в критическую загрузку) и соответствие типов снимку контракта. В CI аудит выполняется для production-сборки.

Скриншоты для отчёта делаются явно (`page.screenshot`) и попадают в `test-results/`; при падении снимки не создаются.

## Покрытие

Пороги Vitest: 85% statements/lines/functions, 80% branches. В область входят `model/**` всех слоёв, `shared/api`, `shared/lib`, `shared/config/env.ts`, `entities/**/api` и `app/router/guards.ts`, включая файлы без тестов; сгенерированная схема и `index.ts` исключены. UI покрывается компонентными тестами и E2E, поэтому процент не описывает всё приложение. Пороги не снижаются ради зелёного CI.

Отчёты: `coverage/index.html`, `playwright-report/index.html` (`npx playwright show-report`). Артефакты E2E могут содержать данные из моков; при добавлении сценариев на реальном стенде ограничьте доступ и срок хранения.

## Как писать тесты

- Сущности: адаптер на полном и пустом ответе, неизвестные значения перечислений, ключи запросов.
- Транспорт и API: подменяйте `fetch` (`vi.stubGlobal`) и проверяйте URL, заголовки и разбор ошибок; не мокайте `apiClient` целиком.
- Формы: валидация, успех, `401`/`429`/сеть, отсутствие повторной отправки. Валидация vee-validate асинхронна и содержит таймер: после `trigger('submit')` нужна реальная пауза, а не только `flushPromises`.
- Ищите элементы по роли и доступному имени, не по классам Tailwind.
- Новые страницы проверяйте прямым переходом и обновлением URL: guard-ы должны выдерживать холодную загрузку.
