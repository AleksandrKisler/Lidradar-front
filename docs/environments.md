# Окружения и конфигурация

| Среда    | Vite mode   | Файл             | Сборка                 |
| -------- | ----------- | ---------------- | ---------------------- |
| dev      | development | .env.development | npm run build:dev      |
| pre-prod | preprod     | .env.preprod     | npm run build:pre-prod |
| prod     | production  | .env.production  | npm run build:prod     |

Vite mode и NODE_ENV — разные вещи: `vite build --mode preprod` остаётся production-оптимизированной сборкой. Dev-сервер с preprod mode не заменяет проверку dist.

## Переменные

- `VITE_APP_ENV`: строго `dev`, `pre-prod`, `prod`.
- `VITE_API_BASE_URL`: `/api` либо HTTP(S) URL. Для внешнего API настройте CORS и CSP; в prod используйте HTTPS.
- `VITE_DEMO_MODE`: строка `true` или `false`. Все шаблонные окружения явно включают демо.
- `DEV_API_TARGET`: адрес локального backend для Vite proxy; не префиксован VITE и не экспортируется приложением.

В `src/shared/config/env.ts` Zod проверяет настройки при старте. Неправильная конфигурация не должна незаметно подменяться fallback-адресом. При такой ошибке приложение не запустится; проверьте консоль и артефакт конфигурации.

`.env.example` → `.env.development.local` для личных настроек. Файлы `.local` исключены из Git и Docker. Приоритет Vite: переменные процесса > mode.local > mode > .env.local > .env. Не храните одинаковые ключи сразу во множестве файлов без причины.

_\*Любые VITE_* публичны._* Ключи сервисов, пароли и серверные токены передаются только backend через секреты CI/хостинга. Не кладите их во frontend даже через masked CI variables.

## Подключение API

1. Установите `VITE_DEMO_MODE=false` в нужной среде.
2. Реализуйте `GET /api/risks/current`, например:

```json
{ "id": "LR-1042", "customer": "Дмитрий Соколов", "amount": 31000, "status": "open" }
```

3. Реализуйте серверное действие признания риска с авторизацией, проверкой текущего состояния и обработкой ошибок. Сейчас кнопка действия доступна только в демо; реальный read-only режим не имитирует сохранение.
4. Для реального действия замените локальную функцию на запрос и обновление подтверждённым сервером результатом; добавьте loading, error, защиту от повторной отправки и интеграционные тесты.
5. В dev работает Vite proxy. В контейнере `/api` возвращает 503 до настройки proxy_pass/ingress, чтобы отсутствие backend было явным.

HTTP-клиент возвращает unknown: схема сущности валидирует ответ. Текущий клиент предназначен для JSON GET, имеет таймаут 10 секунд по умолчанию. При передаче собственного AbortSignal ответственность за его timeout несёт вызывающий код. Запросы с побочными эффектами не повторяются автоматически.

## Как изменять конфигурацию после сборки

Переменные встраиваются во время `vite build`. Передача VITE_* готовому Nginx-контейнеру ничего не изменит: требуется новая сборка. В этом шаблоне используются отдельные артефакты сред из одного commit. Если нужен один и тот же digest во всех средах, внедрите runtime-config.json с валидацией перед mount и no-cache; это другой контракт поставки.

Для размещения в подкаталоге настройте `base` в Vite и соответствующий fallback на веб-сервере; текущая конфигурация рассчитана на корень домена.
