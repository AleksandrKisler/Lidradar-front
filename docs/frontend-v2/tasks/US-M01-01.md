## 3. API и граница поставки

US-M01-01 backend: `89c35df484838e643916828095386fa7bb97cfd5`.
Целевой backend с ADR 0068: `0d06d96b62b03947e6cda10615c8c57324a479f4`.
Целевой SHA-256 OpenAPI обоих изменений:
`9f9766cc4d23e398268aabc68d8adae6db9bf3358bf14953b151f36c617e3027`.
Он включает нейтральный отказ регистрации. На старте сверить SHA коммита
и hash; не копировать случайный dirty OpenAPI из соседней работы.

Backend локально проверен; наличие метода на стенде этим не подтверждается.
Это отдельное согласованное расширение регистрации поверх стабильного релиза,
не разрешение подключать отложенные API других модулей. Backend, миграции,
рабочие ENV и Figma в frontend-задании не изменяются. Deploy/push/merge
и внешняя почтовая доставка не входят в поручение.

| Метод                                             | Запрос / успех                                                                 | Использование                                                                   |
| ------------------------------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| `GET /api/v1/auth/registration`                   | `200 { mode: 'open' \| 'invite_only' }`                                        | Только обычный `/register`: выбрать A/C по свежему ответу                       |
| `POST /api/v1/auth/registration/invitation/check` | `{ code: string }` → `204`, без тела                                           | Проверка кода платформы/сотрудника; гостевой метод без `X-Tenant-ID`            |
| `POST /api/v1/auth/register`                      | `{ displayName, email, password, inviteCode? }` → `201`, user + session cookie | A без кода; B с проверенным кодом. Окончательная серверная проверка сохраняется |
| `GET /api/v1/auth/me`                             | Существующая сессия/членства/права                                             | После регистрации и при восстановлении неизвестного результата                  |

Precheck: `400 INVALID_ARGUMENT` — ошибка запроса; только
`403 INVITATION_INVALID` — непригодный код; `403 ORIGIN_NOT_ALLOWED` — служебный
отказ; `429 RATE_LIMITED` — ожидание по Retry-After; сеть/timeout/5xx — повтор
вручную без утверждения о негодности кода. `404` старого API не открывает B3.
Все ответы precheck no-store. `204` не содержит proof/token/type/tenant/role
и не создаёт/не расходует ничего. Не подменять его пробной регистрацией
или `POST /invitations/accept`.

Precheck имеет отдельный серверный лимит 10 попыток/15 минут; регистрация
сохраняет 5 попыток/час. Клиент не реализует авторизацию этими числами.
`useRetryAfter('lidradar.invitation-check.retryUntil')`: при плохом/отсутствующем
Retry-After запас 60 секунд, после отсчёта нужен ручной повтор.

`400 REGISTRATION_FAILED` и legacy `409 EMAIL_ALREADY_REGISTERED` дают один
нейтральный блок **над формой**: «Не удалось создать аккаунт» /
«Проверьте данные или попробуйте позже.». Не выделять почту как занятую,
не показывать raw message/details. Сохранить данные в памяти и проверенный
контекст B, позволить исправление и явный повтор. Сеть/5xx/неизвестный исход,
отказ приглашения и изменение режима — отдельные состояния, не этот отказ.

Исполнитель синхронизирует контракт штатными `api:sync`, `api:generate`,
`api:check` из чистой копии выбранного backend revision. Если соседнее дерево
менялось, использовать отдельную чистую копию, не сбрасывать его. В
`contracts/source.json` должен быть фактический backend commit; hash хранить
в evidence manifest. Generated вручную не править. Сейчас синхронизация не запускалась.

## 4. Поведение A/B/C

На `/login` две ссылки: «Создать аккаунт» → `/register` и
«У меня есть приглашение» → `/register?flow=invite`.
Одна страница регистрации, общая форма данных и отдельная форма кода.

| Путь | Требуемое поведение                                                                                                                                                                                                     |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A    | Свежий `mode=open`: имя, почта, пароль; пояснение «Заполните имя, электронную почту и пароль, чтобы создать аккаунт.»; «Использовать код приглашения» → пустой B2. Нет поля кода/проверенного приглашения/warning       |
| B2   | `flow=invite`: ввод и проверка кода; `204` автоматически открывает B3 на том же URL. Проверка не зависит от загрузки общего режима                                                                                      |
| B3   | Те же три поля без кода; «Приглашение проверено. Заполните данные для создания аккаунта.»; «Использовать другое приглашение» → пустой B2, сброс проверки и пароля                                                       |
| C    | Свежий `mode=invite_only`: warning «Регистрация закрыта» / «Доступ только по приглашению.» над карточкой. Имя, почта, пароль, его раскрытие и submit disabled. Приглашение/login/legal активны; ссылка приглашения → B2 |

Режим задаёт серверный `LIDRADAR_REGISTRATION_MODE`. Новый frontend ENV,
дата открытия и вывод режима из URL не нужны. На обычном входе получать
свежий режим: `staleTime: 0`, `refetchOnMount: 'always'`, `retry: false`,
`refetchOnWindowFocus: false`; разрешение A требует ответа именно текущего входа,
а не только наличия cached open. До ответа skeleton; сбой — служебная ошибка
с ручным повтором. При `INVITATION_REQUIRED` на POST A прекратить отправку,
перечитать режим и перейти в закрытое состояние по ответу, предложить B.

Имя обязательно, максимум 200 символов; пароль 12–1024; валидная почта.
Локальная ошибка почты: «Введите корректный адрес электронной почты.».
Правила login/reset ради этого текста не менять. Отправка: сохранённые поля,
«Создаём аккаунт…», индикатор и запрет дубля. Форматные ошибки у полей,
нейтральный отказ регистрации у всей формы.

После `201` зафиксировать `account-created` **до** загрузки `/me`. Проверить
состояние сессии, а не только resolved Promise. Новый клиент без организации
с `canCreateOrganization` идёт в существующий шаг «Расскажите о компании»;
сотрудник — в организацию владельца по существующим guards. Не создавать
организацию на регистрации, не присваивать права из вида кода.
На онбординге имя, «Аккаунт», «Выйти» сохраняются.

При ошибке `/me` после `201` повторять только загрузку сессии. Потерянный
ответ POST — `registration-outcome-unknown`: сначала `/me`, при подтверждённой
сессии продолжить; иначе «Не удалось получить результат регистрации.
Попробуйте войти или восстановить пароль.» и существующие переходы.
Автоматического повторного POST нет; guest/401 не доказывает отсутствие аккаунта.
Письмо запускает backend после создания аккаунта независимо от онбординга:
frontend не отправляет дополнительное письмо и не ждёт SMTP для перехода.

Переиспользовать `normalizeInvitationCode` и `INVITATION_CODE_PATTERN` из
team model: убрать пробелы, сохранить регистр, ровно 43 base64url символа.
Автопроверка через **400 мс** полного корректного значения; Enter/стрелка
сбрасывают таймер и вызывают ту же команду. Один inflight; IME до compositionend
не отправляет. Нет запроса для пустого/неполного/неверного значения, автоповтора
после ошибки, на focus/render или по окончании 429. Смена контекста/URL/unmount
отменяет таймер/проверку и отсекает поздний ответ по версии операции.

Инпут 46 px с одной рамкой 1 px, hit-area 44×44, видимая кнопка 36×36,
иконка/spinner 20×20 по центру. Отдельной кнопки снизу нет. Не увеличивать
высоту обёртки до 56; вложенный spinner frame не должен оставаться 16 px.
Действие имеет доступное имя «Проверить код», поле label/error description;
Tab/Enter, видимый фокус, aria-busy и объявление ошибки/успеха без потери фокуса.
Не полагаться только на цвет; предусмотреть место длинного кода и текста ошибки.

Контекст B — память + versioned `sessionStorage` вкладки `{ code, checkedAt }`:
30 минут от первой успешной проверки кода; перепроверка/F5 TTL не продлевают.
Проверять схему, формат, конечность времени, отсутствие будущей даты и возраст.
На F5 сначала серверный precheck, только потом B3. Без/при испорченном/истёкшем
контексте или запрещённом storage — B2, работа в памяти сохраняется.
Имя/email только в памяти; пароль не переносить между сценариями. Пароль,
код и поля не попадают в localStorage, Pinia/global session store, query cache,
query keys, логи/аналитику и общие диагностические вложения. Исключение кода —
только описанный sessionStorage; тестовые артефакты используют синтетику.

Поддержать `/register?code=…` и `?flow=invite&code=…`: прочитать код один раз,
убрать через replace, оставить `flow=invite`; сохранить прочие безопасные query.
Новая ссылка приоритетнее storage. Пустой/повторяющийся/неправильный query code
ведёт к ошибке B2, не A. `validated=true` ничего не подтверждает.
Начальный `RegisterPage loading` из `App.vue` до bootstrap — **без side effects**:
не удаляет query, не читает/пишет контекст и не запускает проверку.

Контекст очищать при другом приглашении, переходе к A/C, финальном отказе
приглашения, TTL, успехе и выходе. Final `INVITATION_INVALID` → B2 с красным !
и видимым кодом, без подтверждения/пароля; имя/email можно удержать в памяти.
Обычный `REGISTRATION_FAILED` этого сброса не вызывает. Скопированная вкладка
может стартовать со снимком sessionStorage браузера: это не серверный proof;
в каждой вкладке обязательна перепроверка, обмен/синхронизация не реализуются.

Матрица на каждом устройстве: login с двумя ссылками; A и B3 — обычное,
локальная ошибка, общая ошибка, отправка, skeleton; B2 — пять основных
состояний из макетов плюс служебные сбои/429/пустое действие; C — только
основное и skeleton. Не создавать ошибки/отправку отключённой формы C.
