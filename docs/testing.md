- **Playwright + axe-core** (`tests/e2e/`): гость (редирект на вход с путём возврата, валидация и нейтральная ошибка входа, страница 404) и владелец организации (Radar со сводкой и лентой, фильтр в адресе и в запросе, карточка риска с командами «взять в работу», рекомендацией, записью действия и исхода и возвратом к ленте с фильтром, закрытие риска через подтверждение, подтверждение оплаты как возвращённой выручки и повтор как обычной после `409`, вердикт «подтвердился», затем «ложное срабатывание» с причиной «это не клиент» и каскадом в статус риска и этап сделки, поток сигналов (заголовок организации, перечитывание ленты по сигналу, работа по REST с предупреждением при `503`), диалоги (поиск и фильтр в адресе, переписка с внешней ссылкой, вложением и удалённым сообщением, подгрузка ранних, возврат к списку на телефоне, переход из карточки риска), настройки (название компании, предупреждение о смене валюты, новая точка, недельный график одним запросом, услуга с диапазоном, отключение и включение), онбординг с возобновлением по серверному статусу, интеграции (Telegram и webhook с секретом один раз, `REMOTE`/`LOCAL` проверка, отключение, закрытие шага онбординга), уведомления (предупреждение о Telegram без привязки, одноразовая ссылка с `noopener`, проверка привязки, полное тело `PUT` со сводкой и тихими часами через полночь, сброс к значению по умолчанию, отключение привязки, карточка в интеграциях), нейтральное «не найдено», запрет гостевых страниц, выход) и менеджер (только вкладка «Уведомления», без раздела интеграций, отказ в разделе владельца), команда (участники с пометкой «вы», защита единственного владельца, код приглашения один раз и его отсутствие в списке, повышение, `409` при гонке через управляемый мок, отзыв доступа и приглашения) и новый сотрудник (без членств — к созданию организации, приём кода с проверкой формата, использованный код, пробелы вокруг кода, переход в организацию). Мок карточки хранит состояние между запросами, поэтому проверяется именно перечитывание после команды, а не локальная подмена; статус привязки Telegram мок меняет только по явному сигналу теста (`confirmTelegramLink`), чтобы фоновые перечитывания не «подтверждали» бота сами; гонка `409` при смене роли имитируется `failNextMemberCommand`. API перехватывается моками `tests/e2e/fixtures/api.ts` по контракту, поэтому набор не требует backend и пароля стенда. Профили: Chromium, Firefox, WebKit, мобильный WebKit.
- **Steiger и локальное правило ESLint**: границы FSD, публичные API, сегменты.
- **`npm run api:check`**: сгенерированные типы соответствуют снимку контракта.
- **TypeScript**: strict, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`; приложение и tooling проверяются раздельно.

```sh
npm run check
npx playwright install
npm run test:e2e
```

E2E сам собирает pre-prod и поднимает preview на 4173. `E2E_BASE_URL=https://… npm run test:e2e` отключает локальный сервер, но моки маршрутов остаются.

Smoke на учебном стенде — `tests/e2e/stand.spec.ts`. Он пропускается, пока не заданы путь к файлу с паролем стенда и адрес dev-сервера, который проксирует `/api`:

```sh
LIDRADAR_STAND_PASSWORD_FILE=../Lidradar/runtime/frontend/password.txt \
E2E_BASE_URL=http://127.0.0.1:5173 npx playwright test tests/e2e/stand.spec.ts --project=chromium
```

Вход выполняется API-запросом, cookie переносится в браузерный контекст, трассы и видео для этого набора выключены: пароль не попадает в артефакты. Скриншоты экранов сохраняются в `test-results/`; smoke только читает стенд и не выпускает ссылку привязки.

## Покрытие

Пороги Vitest: 85% statements/lines/functions, 80% branches. В область входят `model/**` всех слоёв, `shared/api`, `shared/lib`, `shared/config/env.ts`, `entities/**/api` и `app/router/guards.ts`, включая файлы без тестов; сгенерированная схема и `index.ts` исключены. UI покрывается компонентными тестами и E2E, поэтому процент не описывает всё приложение. Пороги не снижаются ради зелёного CI.

Отчёты: `coverage/index.html`, `playwright-report/index.html` (`npx playwright show-report`). Артефакты E2E могут содержать данные из моков; при добавлении сценариев на реальном стенде ограничьте доступ и срок хранения.

## Как писать тесты

- Сущности: адаптер на полном и пустом ответе, неизвестные значения перечислений, ключи запросов.
- Транспорт и API: подменяйте `fetch` (`vi.stubGlobal`) и проверяйте URL, заголовки и разбор ошибок; не мокайте `apiClient` целиком.
- Формы: валидация, успех, `401`/`429`/сеть, отсутствие повторной отправки. Валидация vee-validate асинхронна и содержит таймер: после `trigger('submit')` нужна реальная пауза, а не только `flushPromises`.
- Ищите элементы по роли и доступному имени, не по классам Tailwind.
- Новые страницы проверяйте прямым переходом и обновлением URL: guard-ы должны выдерживать холодную загрузку.
