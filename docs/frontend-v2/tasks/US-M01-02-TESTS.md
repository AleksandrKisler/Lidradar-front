# US-M01-02 · Матрица тестирования и приёмки

Дата: 29.10.2026. Приложение к [согласованному ТЗ](US-M01-02.md), **Accepted**.
Все будущие прогоны — **NOT RUN**. Наличие строки не означает успешную проверку.
Порядок: основная сессия Sonnet завершает код/тесты → QA тестирует, затем
функционально принимает → один UI-агент принимает все три размера.

## 1. Предусловия и критерии

Готовый стабильный снимок A/B/C из US-M01-01, выбранный backend/API,
синтетические имя/password, заведомо занятый и отдельный свободный email.
Для B — действующее приглашение, отдельно platform/member; A только `open`.
Занятость известна тестировщику, не выводится в UI. Новые real-коды получать
штатным способом в разрешённом контуре stage; случайный mock-код не
считать действительным на сервере. Считать лимиты попыток, не сбрасывать
их в общей среде ради удобства. Ошибочные попытки тоже расходуют register limit.

## 2. Группы тестирования

| ID  | Уровень и проверка                                                                                    | Ожидаемое доказательство                                                                                                                                                                         |
| --- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| T01 | Unit/component/E2E: `400 REGISTRATION_FAILED` и legacy `409 EMAIL_ALREADY_REGISTERED`, каждый в A и B | Один и тот же нейтральный UI и состояние; оба кода проверены, не все 400/409 подряд                                                                                                              |
| T02 | Component/E2E: текст и место блока                                                                    | Ровно согласованные две строки над полями; email не occupied/invalid из-за этого отказа; постоянный login не меняется, нет auto redirect/recovery                                                |
| T03 | Component/E2E: сохранение формы                                                                       | Введённые имя/email/password не теряются после отказа, password masked, значения остальных полей не меняются при исправлении только email                                                        |
| T04 | Component/E2E: после отказа email меняют на неверный формат                                           | Устаревший общий блок очищен, локальная ошибка у email с точным текстом; POST не уходит, локальный focusFirstProblem сохранён                                                                    |
| T05 | E2E/a11y: фокус и объявление ошибки                                                                   | После DOM update focus на wrapper с tabindex=-1, role=alert, видимый focus; нет принудительного фокуса email; Tab/ShiftTab/Enter и связь локальных ошибок с полем                                |
| T06 | Unit/E2E: редактирование после подтверждённого отказа                                                 | Любое редактируемое поле очищает устаревший блок; остальные данные/контекст B остаются, ни register, ни email-lookup/precheck по редактированию не вызываются                                    |
| T07 | Unit/E2E: B после отказа                                                                              | Сохраняются verified explanation, «Использовать другое приглашение» и проверенный код; поле кода не появляется, checkedAt/TTL не продлеваются                                                    |
| T08 | E2E: исправленный email + явный повтор A/B                                                            | Payload содержит новый email и прежние имя/password; A без inviteCode, B с тем же кодом; один POST; после 201 нет автоматического третьего POST                                                  |
| T09 | E2E + backend evidence: ещё один отказ с тем же занятым email                                         | Тот же блок, нет session/navigation/mail; код ещё пригоден; existing user и серверные инварианты подтверждены сервером, не mock                                                                  |
| T10 | Component/E2E: задержанная отправка, click/Enter/double click                                         | Один inflight register, поля/submit disabled, spinner/«Создаём аккаунт…», данные сохранены, после подтверждённого отказа можно явно повторить                                                    |
| T11 | Unit/E2E + real API: код отозван/истёк/использован между отказом и повтором                           | Финальный INVITATION_INVALID → B2/красный!, proof/password сброшены; не общий отказ, precheck не обходит сервер                                                                                  |
| T12 | Unit/E2E: register429 с Retry-After                                                                   | Сохранён отсчёт; изменение email/повторный mount не обходит блокировку; по окончании нет auto POST, нужен явный повтор                                                                           |
| T13 | Unit/component: INVALID_ARGUMENT, иной 400/409, Origin/неожиданные ошибки                             | Только два согласованных кода дают registration-rejected; иные ошибки не маскируются как occupied/INVITATION_INVALID, raw details не выводятся                                                   |
| T14 | Unit/E2E:201, затем /me500 или гостевой ответ                                                         | Уже account-created, нет повторного register; retry только /me, resolved guest не считается успешной сессией                                                                                     |
| T15 | Unit/E2E: timeout/потерянный POST-response/5xx/неразбираемый ответ                                    | Reconcile /me; при authenticated штатный путь, при guest неизвестный исход и безопасные login/recovery; edit email не разрешает автоматический/скрытый повтор POST                               |
| T16 | Unit/E2E: F5, другое приглашение, уход/выход и клиентский TTL                                         | Password/PII не восстанавливаются из storage; базовая очистка/повторная серверная проверка B работают; отказ TTL не продлевает                                                                   |
| T17 | E2E: после успешного повтора /me/guards/header/logout                                                 | Platform/A с разрешением → company step, member → организация владельца; новый аккаунт/исправленный email/имя, а не существующий пользователь; на отказе перехода нет                            |
| T18 | E2E + backend mail evidence: письмо                                                                   | Клиент не вызывает дополнительную verification send; отказ не запускает письмо; на успехе recipient исправленный email, dispatch независим от онбординга; внешняя доставка не приписывается mock |
| T19 | E2E: C и C→B                                                                                          | Disabled C не отправляет register и не получает submit-error; активный переход в B сохранён; A не наследует скрытое приглашение B                                                                |
| T20 | Visual/E2E/a11y: A и B на трёх устройствах                                                            | Полная матрица состояний ТЗ, exact-frame desktop и approved-pattern adaptive; 375/промежуточная ширина, длинный email/имя, ошибки/focus/busy/scroll без overflow                                 |
| T21 | Реальный frontend→API: A open и B platform/member в open/invite_only, отказ→исправление→успех         | Нужный backend/hash и фактические payload/status/navigation; нет потребления кода на отказе, один успешный аккаунт, существующие серверные инварианты и письмо доказаны отдельно                 |
| T22 | Серверная регрессия одноразовости/конкуренции + browser duplicate guards                              | Один код не даёт два успеха; UI не шлёт дубль; можно использовать существующий DB/race отчёт именно выбранного неизменённого backend с указанием provenance                                      |
| T23 | Unit/source audit: сообщения и хранение                                                               | Оба кода в messages.ts нейтральны; код ошибки/raw server message/traceID не выводятся в бизнес-блок; password/real invite/cookie не попали в storage/logs/telemetry/evidence                     |
| T24 | Contract/compatibility gate                                                                           | Backend SHA/API hash сверены; api:check и generated согласованы; текущий нейтральный API проверен real, legacy409 проверен fixture; смешанные версии не выданы за полную приёмку                 |

В test-report каждая группа имеет snapshot, AC, fixture, шаги/команду,
expected/actual, exit code и evidence либо причину BLOCKED/UNVERIFIED.
Повторять реальные письма на внешний ящик или менять БД/production ENV нельзя.
Использовать разрешённый mail sink/контролируемую тестовую почту stage и синтетические данные.
Прямые правки серверных таблиц не являются способом реализации frontend.

Существующий backend DB/race-отчёт допускается как серверное доказательство
инвариантов при совпадающем source/backend revision; повтор всего Go-набора
без backend-изменений не требуется. Это не заменяет живую связку frontend/API
T21. Нет базы A/B или real API — соответствующие обязательные группы BLOCKED,
полный tester PASS и финальная приёмка не объявляются; mock-результат отдельно.

## 4. Команды и визуальные доказательства

Из frontend, Node 24.19.0. После передачи завершённого кода tester выполняет
адресные unit и Chromium E2E, затем обязательные проверки WORKFLOW.
Учитывать новые/изменённые тесты существующей модели из фактического diff.

```sh
npm run test:unit -- tests/unit/features/register-form.test.ts tests/unit/pages/invitation-registration.test.ts tests/unit/shared/api-error.test.ts
npm run test:e2e -- tests/e2e/access.spec.ts --project=chromium
npm run check
npm run build:pre-prod
```

Перед финальной приёмкой — штатная матрица браузеров и release checks WORKFLOW:

```sh
npm run build:dev
npm run build:prod
npm run audit:release
npm run test:e2e
```

Дополнительно адресные responsive/a11y и capture для US-M01-02; недостающие
fixtures/test/capture-код пишет только implementer. Команды с preview server
не выполняются одновременно на одном порту 4173. `test:stand` — только при
заранее выбранной разрешённой среде; наличие env/проекта не доказывает прогон.
Существующий baseline-сбой сохраняется в отчёте, не скрывается пропуском теста.

Reference/actual/overlay либо diff для каждого необходимого состояния A/B:
source node + reference-kind, viewport/deviceScaleFactor, браузер/версия,
locale/timezone, fonts-ready, стабильные synthetic inputs/time и snapshot.
Использовать ожидание состояния и `document.fonts.ready`, без arbitrary sleeps.
Не создавать новый browser baseline из собственной реализации без сверки
с Figma. Нельзя снижать thresholds или массово обновлять snapshots ради PASS.
Для service states без отдельного точного кадра честно фиксировать проверку
адаптивности/согласованного образца, а не выдумывать отсутствующий node.

В этой подготовке команды продукта не запускались. Проверка Markdown/конфигураций
не является тестированием US-M01-02 или доказательством её приёмки.
