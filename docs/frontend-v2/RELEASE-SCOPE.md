## 2. Решения по пунктам 1–5 для релиза

### Время

Не считать `now - dueAt` ожиданием клиента; не извлекать порог из `reason`, не брать произвольное последнее сообщение за начало ожидания. Не называть календарную длительность рабочей. Для закрытого риска доступны существующая дата закрытия и сохранённые факты; растущий таймер не показывается. Правила выявления/эскалации риска не меняются.

### Вкладки Radar

Без чисел сохраняется согласованный смысл группировки, который уже поддерживается API:

- «Все активные» → `active=true`.
- «Новые» → `status=OPEN`.
- «В работе» → `status=ACKNOWLEDGED&status=ACTED`.

ACTED остаётся отдельным статусом «Действие записано», но входит в рабочую группу. После записи действия карточка не пропадает из «В работе». Это группировка существующих статусов на frontend, без изменения серверной политики. В запросе нельзя смешивать active и status.

Выбор группы/фильтров сохраняется в URL и query keys; смена tenant, группы или фильтра сбрасывает cursor. Сводка получает только общие location/type/severity фильтры, без status/active. Считать общие числа по загруженной странице и выполнять N запросов ради чисел запрещено.

### Действия, исход и заметки

Не называть доступный набор «полной историей». Действия и этапы показываются по реально прочитанным данным; последний исход сделки — отдельным явно подписанным блоком, а не обещанием всех прежних исходов. История этапов читается только с разрешённым правом.

Существующие поля записи заметки сохраняются. После успешного POST можно подтвердить сохранение заметки, но интерфейс не обещает её повторное чтение. У поля нужна короткая подсказка «Повторный просмотр заметок пока недоступен». Заметка не становится доступной историей через localStorage, fixtures или объединение несвязанных сообщений. Полное чтение заметок/исходов остаётся в backlog.

### Оплаты и неизвестный результат

- Исход PAID сам по себе не подтверждает выручку. Показатели меняются только после подтверждённого ответа сервера и перечитывания данных.
- Потерянный ответ: сохраняется исходный контекст user/tenant/сделки, ключ и тело; разрешён повтор этой же отправки с прежним ключом. Текст кнопки «Повторить отправку» прямо соответствует действию. Новый ключ автоматически не генерируется.
- `RECOVERED_ALREADY_ATTRIBUTED`: объяснить, что возвращённая выручка по сделке уже учтена. Владельцу с `analytics.read` доступен переход к существующей аналитике для сверки. Менеджеру — понятное обращение к владельцу, без ссылки в недоступный раздел и без запроса будущего GET.
- `IDEMPOTENCY_KEY_EXPIRED` и `IDEMPOTENCY_CONFLICT`: исходная отправка остаётся заблокированной; предложить сверку владельцем/оператором. Не превращать её автоматически в ORGANIC или новую оплату.
- Сумма `confirmedRecovered` из детали не является доказательством результата конкретной отправки, особенно ORGANIC. По одному перечитыванию общей суммы нельзя объявлять «эта оплата сохранена» или «оплаты не было».
- Сохранить действующие суммы, валюты, цепочки доказательств и ограничения сервера. Отдельная реальная доплата — самостоятельное осознанное намерение, а не способ обойти конфликт предыдущей команды.

## 3. Другие ограничения данных в оболочке

- Под организацией допустимо достоверное «N точек». Города в модели нет; не выводить «Москва» из timezone и не выдавать часовой пояс за адрес.
- Не подтверждать исправность бизнес-источника Telegram по `onboarding.facts.liveConnections`: это число всех источников со статусом, отличным от DISCONNECTED, включая ERROR. `telegramLinked` относится к личным уведомлениям.
- Зелёный статус конкретного источника допустим только по разрешённому ответу интеграции/health с правильным провайдером и актуальным состоянием. Если такого ответа нет, скрыть статус либо оставить нейтральный вход «Источники сообщений». Ошибка/устаревший снимок не называется текущим успешным подключением. Менеджер не получает права управления интеграциями.
- Рекомендация текущего API — шаблон по типу риска. Подпись должна описывать «Рекомендацию по типу риска», без обещания персонализированного AI-разбора переписки.

## 4. Приоритет качества frontend

1. Закончить текущий пилот F01/F02 и предъявить G01: визуальное соответствие desktop/tablet/phone, все карточки длинных лент, адаптивная деталь, формы, обратная навигация и сохранение состояния.
2. Сохранить рабочие команды и права: действия/исходы/этап/оплата, двойной submit, неизвестный результат, 401/403/404, переключение организации.
3. Довести состояния: initial loading, refreshing, error, empty, unavailable, offline/stale, локальные ошибки команд, сохранение черновиков. Неизвестное не заменяется нулём.
4. Обеспечить доступность: keyboard/focus, осмысленные disabled-подсказки, доступные имена и ошибки, длинные строки, zoom/reflow, reduced motion, таблицы без скролла всей страницы.
5. Закрыть технические проверки, стабильность визуального evidence и CSS-бюджет. Не ослаблять проверки, лимиты или browser coverage ради PASS.
6. После пользовательской приёмки G01 продолжать F03–F08 по WORKFLOW, применяя этот же контрактный предел ко всем разделам. Само изменение приоритета не является приёмкой G01.

## 5. Критерии приёмки текущего контура

- RC-01: нет diff backend/OpenAPI/миграций/прав от этой поставки; вызовы соответствуют стабильному контракту и роли.
- RC-02: на NO_RESPONSE и другом типе риска показаны реальные dueAt/detectedAt; нет ложного рабочего таймера, разбора reason или ложных дат из последних сообщений.
- RC-03: вкладки без чисел правильно запрашивают группы, ACTED остаётся в «В работе»; back/reload/tenant/cursor работают.
- RC-04: переключение статусной вкладки и закрытие риска не обнуляют подтверждённо возвращённую выручку; подпись — «За всё время».
- RC-05: действия и последний исход перечитываются после reload; UI не обещает полного журнала и не восстанавливает отсутствующие заметки фиктивными данными.
- RC-06: подтверждение оплаты, двойной клик и потеря ответа используют существующую идемпотентность. Менеджер получает доступный путь при конфликте; нет запрещённых запросов и автоматических новых ключей.
- RC-07: недоступный город/статус источника/персонализированная рекомендация не выдумываются. Ошибка данных не превращается в успешный статус или 0.
- RC-08: на 1440/834/390 и штатных минимальных ширинах нет потери действий/данных, горизонтального скролла всей страницы и неработающих меню/диалогов; длинные строки и zoom проверены.
- RC-09: формы, busy/errors, keyboard/focus и recovery проверены в браузере; скриншоты относятся к финальному diff и воспроизводимому dataset/clock.
- RC-10: `npm run check`, применимые builds/release audit и штатные mock browser-проекты выполнены с реальными результатами. Существующие FAIL и неисполненные проверки явно указаны, не подменены историческим PASS.
- RC-11: реальный backend/Telegram/email QA отделён от mock/frontend QA. Готовность UI не объявляется закрытием остальных release-gates продукта.
- RC-12: для US-шагов, зависящих от отложенного API, записано «отложено» либо соответствие текущему доступному пути; исходный буквальный шаг не получает фиктивный PASS. Backend user-stories не переписываются этой поставкой.
