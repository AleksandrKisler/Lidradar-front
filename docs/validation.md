## Что выявила проверка на стенде

- `dev-data` отказывался поднимать фикстуры на схеме `000022` — исправлено на стороне backend (константа `SchemaVersion`).
- `GET /api/v1/risks` возвращал `500` для любой учебной организации: все фикстурные риски имеют `source = MANUAL`, а доменная проверка знала только `RULE` и `HYBRID`. Исправлено в домене backend; Radar и лента после этого работают на реальных данных (см. скриншоты в отчёте о работе).
- Внутренние ошибки Risk API не попадали в журнал сервера — добавлено событие `risk.request.failed` с `trace_id`.
- Матрица ширин нашла четыре переполнения: карточки не сжимались в колонках (`min-w-0` у `UiCard`), длинные коды причин в карточке риска не переносились, разделённая раскладка переписок начиналась на 768 px рядом с боковой панелью (теперь с 1024), заголовок переписки не сжимался. Отдельно: элементы `sr-only` (абсолютное позиционирование) внутри прокручиваемых таблиц растягивали страницу — области прокрутки стали `relative`.
- Блок администрирования опустил покрытие функций ниже порога (большой read-API без тестов): добавлены тесты всех запросов и composable-хуков сущностей, покрытие выросло до 94/86/94/96 %.
- Аналитика на стенде: 30-дневный ряд не помещался в карточку и свежие столбцы уходили за горизонтальную прокрутку — график стал подстраиваться под ширину карточки для любого окна до 366 дней.
- Мобильный профиль axe отметил прокручиваемую таблицу участников без фокусируемого содержимого (когда все кнопки отключены защитой последнего владельца) — область получила `tabindex` и имя.
- Полный параллельный прогон Playwright вскрыл гонку в диалоге подключения источника: две отправки в окне асинхронной проверки формы (двойной клик, клик и Enter) создавали два подключения. Исправлено синхронным замком отправки и состоянием занятости кнопки на время проверки; добавлен unit-тест.

## Известные ограничения инкремента

- Реализованы Radar, карточка риска с командами, действиями, исходами, вердиктом и подтверждением оплаты, realtime-обновления по SSE, диалоги только для чтения, онбординг с возобновлением по серверному статусу, настройки компании, точек, графика и услуг, интеграции источников, уведомления с личной привязкой Telegram, команда с одноразовыми кодами приглашений, аналитика с точностью сигналов и оплатами, данные и согласие на обучение, администрирование платформы, ручной перевод этапа сделки с неизменяемой историей; карточки укрепления LR-FE-031…033 — следующий шаг.
- Автопроверка привязки Telegram ограничена: раз в 5 с, только на видимой вкладке, не более 24 попыток на одну ссылку; дальше — ручная проверка или новая ссылка. Идентификаторы Telegram интерфейсу не передаются.
- Приглашения без писем: код показывается один раз и передаётся владельцем вручную; список приглашений кода не содержит. Защита последнего владельца на клиенте — подсказка, окончательное решение принимает сервер (`409 LAST_OWNER`).
- В аналитике визуализирован только дневной ряд возвращённой выручки; остальные ряды ответа (сообщения, риски, все оплаты) показываются итогами и в таблицах. Таблица оплат без фильтров, возвратов в модели нет. Границы окна для точности — начало календарного дня организации с учётом переходов на летнее время; ответный период сервера остаётся авторитетным.
- На учебном стенде нет менеджера и администратора платформы: эти роли, а также мутации (команды, оплаты, приглашения) проверяются только на мок-API; набор стенда не меняет данные. Макеты узких экранов и администрирования утверждены комплектом v0.3 (листы 17–32 в `docs/front-end/mockups` backend-репозитория; GAP-DESIGN-014/015/018 закрыты 2026-09-25): матрица проверяет семантический reflow автоматически, визуальное соответствие сверяется вручную по PNG листов 29–31.
- Телеметрия по умолчанию никуда не отправляется: приёмник включается только адресом `VITE_TELEMETRY_ENDPOINT`; Web Vitals не собираются, записываются сбои API и длительность навигации.
- Этапы сделки: матрица переходов повторяет модель данных, но окончательное решение за сервером (`409 INVALID_STAGE_TRANSITION` перечитывает сделку). Выигрыш не фиксирует оплату — она подтверждается отдельно, о чём говорит диалог подтверждения. На стенде этап не менялся: проверено чтение истории.
- Администрирование проверено только на мок-API: у учебного стенда нет пользователя с правом администратора, поэтому smoke подтверждает лишь нейтральный экран без admin-запросов. Списки ограничены лимитом 50/100/200 без курсоров, как в контракте; фоновых обновлений нет, только ручное «Обновить» со временем снимка.
- Согласие на обучение: экран без макета собран по тексту блока 12; имена авторов выдачи и отзыва видит только владелец (через список участников), остальным показывается нейтральная подпись. Копия не обещает удаления истории и сформированных наборов, потому что политика backend этого не заявляет.
- Отдельной ленты уведомлений внутри приложения нет: контракт её не отдаёт (GAP-API-013); переключатель «Внутри LidRadar» управляет доставкой на стороне сервера.
- В списке диалогов нет фильтров по точке и подключению в интерфейсе (параметры адреса принимаются): справочники точек и подключений появятся вместе с настройками и интеграциями.
- Контракт не отдаёт список вердиктов по риску: после перезагрузки панель оценки снова показывает форму, а записанный вердикт виден только по статусу `FALSE_POSITIVE`.
- История подтверждений оплаты в карточке ограничена итогом `confirmedRecovered` из read model: список событий выручки контракт не отдаёт.
- Полная история действий приходит из карточки в сокращённом виде (тип и время): заметки и автор в read model контракта отсутствуют.
- Лента обновляется по сигналам `/events`, при возврате фокуса, возврате сети и по кнопке; поток — ускоритель, время последнего снимка остаётся видимым.
- Внешняя ссылка в карточке показывается, только если её построил сервер; для каналов без deeplink выводится причина.

## Регрессия QA-02 — 30 сентября 2026 года

Исправлена двойная отправка формы услуги. Синхронная блокировка устанавливается
до асинхронной валидации и снимается после завершения сохранения и обновления
каталога либо после ошибки. Поля, отмена и кнопка отправки используют это состояние.
Общая форма применяется при создании, редактировании и в онбординге.

- Два регрессионных теста до исправления воспроизводили два запроса вместо одного
  для создания и редактирования. Теперь повторные submit до завершения валидации
  и во время запроса дают ровно один POST/PATCH и одно событие `saved`.
- Проверены повтор после отказа API с сохранением ввода, создание следующей
  услуги после успеха и повтор после исправления неверного диапазона цен.
- `CHOKIDAR_USEPOLLING=1 npm run check`: 326 тестов в 58 файлах, все ворота
  пройдены. Покрытие statements/branches/functions/lines:
  94,71/86,62/94,78/96,53 %. `npm run audit:release` также пройден.
- Ручной прогон в Chrome на dev-стенде, `small@lidradar.test`: неверный диапазон
  2000–1500 отклонён; после исправления на 1000–1500 двойной клик создал одну
  услугу «QA30.09 двойной клик». Каталог вырос с 6 до 7 записей; после reload
  и независимого GET `/api/v1/services` подтверждена одна новая запись.

Это защита одной открытой формы от повторного submit. Контракт каталога не
поддерживает серверную идемпотентность: повтор после потери ответа или из другой
вкладки требует отдельного решения. Автоматические повторы мутаций отключены.
Известный аналогичный дефект формы точки в этом исправлении не затрагивался.
