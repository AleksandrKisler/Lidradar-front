## Цель и формулировка US

Как новый клиент LidRadar, я хочу сначала проверить полученное приглашение, а затем на той же странице заполнить данные регистрации, чтобы создать аккаунт и перейти к созданию своей компании.

Предусловия: пользователь не авторизован, имеет действующий неиспользованный код платформы и свободный адрес почты.

Сохраняем номер US-M01-01. Используем один маршрут `/register`, два основных шага (код → данные) и служебные состояния. Приглашения сотрудников используют ту же проверку и форму; после регистрации маршрут определяется видом приглашения по существующим правилам.

Согласовано пользователем: две ссылки со страницы входа, выбор сценария через `flow=invite`, отдельная проверка кода перед общей формой, автоматическая проверка с ручным действием, блокировка ввода на время запроса, закрытая общая регистрация по серверному ENV. Значения задержки, срока клиентского контекста и лимита запросов — предлагаемые настройки реализации.

Черновые заметки о реализации, файлах и проверках: [us-m01-01-implementation-plan.md](./us-m01-01-implementation-plan.md). После согласования макетов этот материал уточняется при обновлении US и подготовке решения.

## Точки входа и тексты

На странице `/login` остаётся ссылка **«Создать аккаунт»**, рядом добавляется **«У меня есть приглашение»**. На узких экранах ссылки переносятся на отдельные строки с полноценной областью нажатия.

«У меня есть приглашение» ведёт на `/register?flow=invite`. Формулировка описывает намерение и не обещает вход в существующий аккаунт по одному коду.

В закрытом режиме «Создать аккаунт» открывает `/register`: над карточкой расположен warning-баннер **«Регистрация закрыта»** / **«Доступ только по приглашению»**. Поля имени, почты и пароля видимы, но отключены; кнопка «Создать аккаунт» и показ пароля также отключены. Ссылка **«Использовать код приглашения»** → `/register?flow=invite` остаётся активной, как и «Уже есть аккаунт? Войти» и правовые документы. Призыв заполнить данные в этом состоянии не показывается. Это условное состояние общей формы при серверном `LIDRADAR_REGISTRATION_MODE=invite_only`, полученном через `GET /auth/registration`; служебная пометка в Figma вынесена за пределы интерфейса.

При открытом режиме «Создать аккаунт» сразу показывает общую форму. Если пользователь приходит с приглашением, оно всё равно проверяется и применяется.

У общей формы два контекста: после успешной проверки `flow=invite` — сообщение «Приглашение проверено» и ссылка «Использовать другое приглашение»; у обычного `/register` в `open` — нейтральное пояснение и ссылка «Использовать код приглашения» → `/register?flow=invite`. У обычной формы сообщения об уже проверенном приглашении нет. Оба desktop-варианта согласованы пользователем 29.10.2026; [кадры и статусы](./us-m01-01-design-review.md).

| Вход на страницу            | `invite_only`                     | `open`                             |
| --------------------------- | --------------------------------- | ---------------------------------- |
| `/register`                 | Warning и отключённая форма       | Имя, почта, пароль без приглашения |
| `/register?flow=invite`     | Ввод кода → после проверки данные | Ввод кода → после проверки данные  |
| Персональная ссылка с кодом | Автоматическая проверка → данные  | Автоматическая проверка → данные   |

`flow` выбирает намерение, режим сервера определяет доступность. Изменение URL не разрешает регистрацию без кода в `invite_only`. Неизвестный `flow`, пустое значение и массив значений трактуются как обычный вход `/register`. Только единственное строковое значение `invite` включает сценарий приглашения. Переданный код запускает сценарий приглашения независимо от `flow` и не может быть молча проигнорирован даже в `open`.

Внутри страницы используем явные состояния: загрузка режима, закрытая регистрация, ввод/проверка/ошибка кода, данные аккаунта, создание аккаунта, восстановление сессии. Успех проверки переключает компонент без перехода на другой маршрут; адрес остаётся `/register?flow=invite`. Параметр `step=details` не нужен и не открывает форму. При переключении шага фокус переводится на заголовок нового шага или первое поле.

## Первый шаг: проверка приглашения

- Заголовок: **«Регистрация по приглашению»**.
- Пояснение: **«Введите код, который вам передали. После проверки вы сможете создать аккаунт.»**
- Поле: **«Код приглашения»**, один текстовый ввод с поддержкой вставки.
- Подсказка: **«43 символа. Скопируйте и вставьте код целиком.»**
- Внутри поля справа: **синяя кнопка со стрелкой вправо**, область нажатия 44×44 px. Отдельной кнопки снизу нет. Доступное название и подсказка: **«Проверить код»**. Во время запроса стрелка заменяется индикатором проверки.
- Дополнительное пояснение под полем: **«Код проверится автоматически после ввода.»**
- Ссылка снизу: **«Уже есть аккаунт? Войти»**.

Название «Проверить код» отражает действие сервера; «Отправить код» может восприниматься как отправка пользователю нового кода.

Кнопка выделена основным синим цветом; текст поля не заходит под неё. Desktop-кадр со встроенной стрелкой и высотой поля 46 px согласован пользователем 29.10.2026. Нажатие Enter выполняет ту же проверку.

## Проверка кода

1. До запроса выполняется локальная проверка: нормализация пробелов по существующим правилам, ровно 43 символа `base64url`, регистр сохраняется. Неполный или неверный по формату код не отправляется на сервер.
2. После ввода или вставки полного корректного значения запускается автоматическая проверка с задержкой 400 мс. Нажатие кнопки или Enter отправляет его сразу и отменяет ожидающую автоматическую отправку.
3. На время запроса поле и кнопка блокируются, стрелка заменяется индикатором проверки, состояние «Проверяем код…» объявляется экранному диктору. Одновременно допускается один запрос. Блокировка начинается непосредственно перед отправкой и сохраняется до ответа или ошибки.
4. Успех → сохраняется временный контекст приглашения и на той же странице автоматически показывается второй шаг — данные аккаунта. Дополнительное подтверждение пользователя не требуется.
5. Неверный, просроченный, отозванный или использованный код → **«Код не подходит: он неверен, просрочен, уже использован или отозван. Попросите новый.»** Поле разблокируется, значение сохраняется, фокус возвращается к полю.
6. Сбой сети, тайм-аут или ошибка сервера → **«Не удалось проверить код. Попробуйте ещё раз.»** Поле разблокируется; повтор — кнопкой или Enter. Не объявляем код неверным.
7. При ограничении частоты показывается **«Слишком много попыток. Повторите через … с.»** Повторная отправка недоступна до окончания указанного сервером срока; поле можно исправить.

Автоматическая проверка выполняется один раз для нового полного значения. После ошибки неизменённое значение не запускает цикл повторных запросов. При уходе со страницы или смене `flow` запрос отменяется; поздний ответ не переключает состояние. Используется существующий тайм-аут API-клиента 15 секунд. После окончания ограничения частоты повтор выполняется вручную.

При ручной отправке пустого поля: **«Введите код приглашения»**. При ошибке длины/формата: **«Проверьте код: нужно вставить все 43 символа.»** Ошибка появляется под полем и связана с ним для вспомогательных технологий.

## Второй шаг: единая форма регистрации

После успешной проверки `/register` показывает:

- Заголовок **«Создать аккаунт»**.
- Подзаголовок **«Приглашение проверено. Заполните данные для создания аккаунта.»**
- Поля **«Имя»**, **«Электронная почта»**, **«Пароль»**.
- Кнопку **«Создать аккаунт»**, действующие ссылки на правовые документы и **«Уже есть аккаунт? Войти»**.
- Второстепенную ссылку **«Использовать другое приглашение»** → очистка контекста и возврат к первому шагу на том же адресе `/register?flow=invite`.

Поля кода нет ни в одном варианте формы регистрации. Результат проверки не означает резервирование приглашения: оно может истечь или быть отозвано до отправки формы.

При ошибке занятой почты пользователь исправляет почту на этой же странице; приглашение остаётся доступным. Если при окончательной отправке приглашение стало недействительным, форма сохраняет имя и почту, очищает пароль и показывает сообщение с действием **«Проверить другое приглашение»**. После новой проверки восстанавливаются имя и почта, пароль вводится заново.

После регистрации по коду платформы открывается «Шаг 1 из 4 — Расскажите о компании»; по коду сотрудника — соответствующее рабочее пространство по существующему сценарию. Подтверждение почты, шапка и правила пароля сохраняют действующие требования US.

Если открытый режим успел закрыться и отправка формы без кода получила `INVITATION_REQUIRED`, имя и почта сохраняются в памяти, пароль очищается, режим перечитывается и предлагается перейти к вводу кода. Если сервер уже подтвердил создание аккаунта (`201`), а `/auth/me` не загрузился, повторяется только получение сессии; повторно создавать аккаунт или использовать код нельзя.

## Ссылки, обновление страницы и обход маршрутов

- Новая персональная ссылка: `/register?flow=invite#code=…`. Код считывается, сразу удаляется из адреса через замену текущей записи, затем проходит ту же автоматическую проверку. Промежуточный экран виден в состоянии «Проверяем…», повторный ввод не требуется.
- Существующие ссылки `/register?code=…` продолжают работать: значение считывается, удаляется из адреса, выставляется `flow=invite`, затем выполняется проверка. Остальные параметры сохраняются. При двух источниках кода принимается только совпадающее единственное значение; противоречивые/множественные значения дают ошибку ссылки и ручной ввод.
- В закрытом режиме обычный `/register` показывает закрытое состояние, даже если в хранилище остался прежний код. Контекст восстанавливается только для `flow=invite`; новая ссылка с кодом заменяет прежний контекст до отправки проверки. Нельзя открыть форму одним произвольным параметром вроде `validated=true`.
- Для первой реализации контекст хранится в памяти приложения и `sessionStorage` данной вкладки: код и время предварительной проверки, без пароля. Предлагаемый срок контекста — 30 минут; это срок удобства интерфейса, он не продлевает действительность самого приглашения. TTL не продлевается автоматически при обновлении страницы. После обновления контекст повторно проверяется сервером до показа формы; при сетевой ошибке доступен повтор. При недоступном/повреждённом хранилище сценарий работает в памяти, после обновления потребуется код.
- Контекст очищается после успешной регистрации, истечения срока, выбора другого приглашения и выхода. Код не попадает в аналитику и журналы ошибок.
- Клиентский контекст управляет интерфейсом. Окончательное разрешение всегда даёт сервер при создании аккаунта.
- Действие «Использовать другое приглашение», истечение клиентского контекста и ошибки приглашения при регистрации возвращают к проверке; имя/почта могут оставаться в памяти текущей страницы, пароль очищается. Они не записываются в `sessionStorage`. При обычной перезагрузке восстанавливается только код.

## Изменения сервера и клиента

Сейчас серверный контракт проверяет приглашение при `POST /api/v1/auth/register`; отдельного публичного метода предварительной проверки в описанном контракте нет. Поэтому одного изменения интерфейса недостаточно.

Предлагаемый новый метод: **`POST /api/v1/auth/registration/invitation/check`**, тело `{ code }`, без авторизации. Действующий код → `204`; недействительный → `403 INVITATION_INVALID`; неправильное тело → `400`; превышение лимита → `429` с `Retry-After`. Это предложение нового контракта, а не существующий метод.

Метод проверяет допустимые коды платформы и сотрудников по тем же правилам, что регистрация, имеет отдельный ограничитель частоты и `Cache-Control: no-store` для всех ответов. Он не создаёт пользователя или сессию, не выдаёт права, не резервирует и не расходует код. Не требует `X-Tenant-ID`, не возвращает данные организации или вид кода. Пустой код всегда отклоняется, включая `open`. Некорректный формат тела → `400 INVALID_ARGUMENT`, непригодный непустой код → `403 INVITATION_INVALID`. Операционные сбои не преобразуются в недействительность кода.

Предлагаемое ограничение: отдельный scope `REGISTRATION_INVITATION_CHECK_IP`, 10 запросов за 15 минут на IP через существующий общий PostgreSQL limiter, независимо от `REGISTER_IP` (регистрация — 5 в час). Неверные попытки также учитываются. Точные пороги фиксируются в серверном решении перед реализацией. Новая бизнес-таблица для проверки не нужна; необходимость расширения ограничения допустимых scope в существующей схеме проверяется при реализации.

Текущий `POST /auth/register` можно сохранить: клиент передаёт проверенный `inviteCode` из контекста без отображения поля. Сервер повторно проверяет приглашение и погашает его по существующим правилам успешной регистрации. Предварительная проверка не заменяет эту проверку. Гонки, занятая почта и одноразовость сохраняют правила ADR 0057.

На клиенте нужны управление состояниями существующей `RegisterPage`, форма проверки с защитой от двойной отправки, временный контекст, обработка ссылок и `flow`, закрытое состояние `/register`, изменение `LoginPage` и удаление видимого поля кода из `RegisterForm`. Новый маршрут не добавляется.

В текущем frontend-релизе действует ограничение стабильным API ([RELEASE-SCOPE.md](../frontend-v2/RELEASE-SCOPE.md)). Этот пакет подготовлен отдельно: доступность реальной предварительной проверки зависит от поставки нового серверного метода. Локальная проверка длины не может подменять ответ сервера. Подготовка не изменяет ограничения текущего релиза и не добавляет несуществующий метод в рабочий контракт или fixtures.

Персональная передача кода в текущем контракте не привязывает его к человеку или адресу почты: воспользоваться им может получатель кода. Если нужна именно привязка к конкретной почте, это отдельное изменение правил выпуска и принятия приглашений.

## Период закрытой регистрации

До 15 января сохраняется серверный режим `invite_only`; регистрация с действующим приглашением работает. Для планирования дата трактуется как **15 января 2027 года** — год выведен из даты обсуждения и требует подтверждения перед назначением выпуска.

Дата не зашивается в клиентскую логику. 15 января не запускает автоматическое открытие: переход в `open` выполняется управляемо на сервере, когда общая регистрация готова. После переключения используется та же форма без предварительного кода. При неизвестном режиме или ошибке его получения форма без приглашения не открывается; показываются загрузка/ошибка с повтором.
