## Данные и сценарии

Используй существующие endpoints с `X-Tenant-ID`:
`GET /api/v1/integrations`, `POST /api/v1/integrations/{provider}/connect`,
`GET /api/v1/integrations/{connectionId}/health`,
`POST /api/v1/integrations/{connectionId}/health/check`,
`DELETE /api/v1/integrations/{connectionId}`. Не создавай новых API.

**Различай состояние источника, результат проверки и доставку сообщения.**
GET health читает сохранённое состояние; `checkedAt` здесь — время чтения,
а не удалённого опроса. POST check возвращает `verification: REMOTE | LOCAL`.
REMOTE сам по себе не означает исправность: учитывай возвращённый health.
LOCAL не показывай как «Telegram проверен». Даже успешная удалённая регистрация
не доказывает получение нового сообщения. Даты бери из соответствующих полей
и показывай в timezone организации, null — как отсутствие факта.

Первичная загрузка, пустой список, первый сбой, повторное обновление и его
сбой — разные состояния. RefreshError сохраняет уже известные данные и явно
показывает неудачное обновление; FirstError не выдаёт отсутствие ответа за
пустой список. CheckError не превращает источник в ERROR автоматически;
SourceError основан на подтверждённом ответе источника. Не скрывай все карточки
из-за ошибки действия одной карточки. Повтор адресный, двойная отправка
заблокирована, результаты относятся к своему connectionId и tenantId.

Подключение: название, точка/вся организация, токен; текущая валидация,
пять коротких шагов и подробная инструкция из 16 шагов с возвратом. Сохрани
контекст формы при просмотре инструкции; после закрытия/завершения соблюдай
действующее очищение токена. Не сохраняй токен в URL, storage, query cache,
логах, скриншотах или evidence. Не читай реальные credentials ради визуального QA.
Сохрани текущую безопасную обработку отказа токена, сети, 409 занятости бота
и запрет дублей. Ответ 201 может содержать ERROR — не показывай «Активно»
только на основании успешного HTTP-кода.

Отключение: подтверждение с объяснением остановки новых сообщений и сохранения
истории; отмена без запроса. При подтверждённом отключении убери проверку и
повторное обычное отключение, оставь инструкцию. `503` именно DELETE по текущему
контракту означает локальное отключение с неподтверждённым удалением настройки
у Telegram: критическое оформление «Отключено», точное пояснение и
«Повторить отключение». Произвольный timeout/503 другого запроса этого не доказывает.
Не объявляй полный удалённый успех по сохранённому DISCONNECTED.

До реализации закрой в плане два известных ограничения без выдуманных полей:

1. В текущем ChannelConnection нет username бота. Используй реальное имя
   подключения/провайдера и предусмотренный данными fallback. Не получай
   username из токена и не обращайся из браузера напрямую в Telegram API.
   Если конкретный обязательный элемент макета нельзя заполнить по контракту,
   зафиксируй это узкое отличие, не меняя backend.
2. В list/health нет отдельного надёжного признака незавершённого удалённого
   удаления. Опиши время жизни известного результата DELETE 503, восстановление
   при remount и поведение после reload. Не выдавай клиентский маркер за факт
   сервера. Учти, что DELETE 204 означает также «уже отключено»: не обещай,
   что повтор гарантированно удалил настройку Telegram, без доказательства
   доступного контракта. Если AC требует неподдержанной гарантии, покажи
   конкретный разрыв и вариант решения владельцу; продолжай независимые части.

Источник переписки организации и личная привязка уведомлений независимы.
Статус одного не подтверждает другое. Ошибка личной привязки не скрывает
источники; её повтор и переход к существующим Настройкам ограничены этой строкой.
Не реализуй заново весь раздел уведомлений. MAX не подключается; TEST/IMPORT/
GENERIC_WEBHOOK из существующего API не превращай в Telegram и не удаляй.

Соблюдай `integration.manage`: менеджер не получает управление/данные раздела,
прямой URL показывает предусмотренное недоступное состояние. При смене
организации или прав сбрасывай чужой контекст формы и результатов операций,
отменяй/игнорируй поздние ответы. Не показывай данные прежнего tenant под новым.

В смешанных тестовых файлах выбирай отдельные сценарии интеграций через
точный фильтр либо выделяй их в отдельный spec, сохраняя чужие тесты.

Для E2E создай/используй выделенный integrations spec. Перед запуском выполни
`npx --no-install playwright test` с точными путями/grep, project и `--list`;
убедись, что выбраны только интеграции. Затем запусти тот же набор без `--list`.
Пустой фильтр исправляй, а не заменяй полным suite. Начни с Chromium и трёх
viewport; другой браузер нужен только для конкретного риска этой работы.

Проверь: загрузку/пустое/ошибку/повтор, сохранение данных при refresh-error,
REMOTE/LOCAL и ERROR-result, connect validation/pending/rejection/409,
инструкцию и возврат, disconnect cancel/204/503/retry/unknown result,
независимость уведомлений, права, смену tenant и поздние ответы, длинные данные,
фокус и адаптивы. Числовую/статусную логику не дублируй десятками дорогих E2E.
Переходы к связанным экранам проверяй только как часть сценария интеграций.

и доставка реального Telegram-сообщения не считаются доказанными моками.

**Не запускай** общий `npm run check`, общий `test:coverage`, нефильтрованные

`audit:release` и комплект релизных сборок. Не меняй CI, thresholds, assertions,

## Организация и завершение

При делегировании используй узкий brief по `CODEX-TASK-BRIEF.md`, один автор
на файл, без вложенных агентов и дополнительных чатов. Интегрируй изменения,
зафиксируй snapshot с SHA inputs, включая untracked, затем передай
lidradar-qa TEST → FUNCTIONAL и lidradar-visual-review три адаптива **только
интеграций**. Пока снимок проверяется, не меняй inputs. После исправления —
новый снимок и затронутые проверки. Общие требования ролей не расширяют
разрешённую здесь область тестирования.

Обнови STATUS и evidence, сохраняя исторические отчёты. В финале: story IDs,
что реализовано, файлы, точные команды/exit codes, снимок, evidence,
TEST/FUNCTIONAL/UI по интеграциям, ограничения API и непроверенные живые
сценарии. Полную регрессию и общую приёмку приложения отметь **DEFERRED до
завершения frontend**. Не называй локальный PASS интеграций релизным PASS.
Доведи разрешённую реализацию и адресные исправления до готовности;
не останавливайся на плане или одном демонстрационном экране.
