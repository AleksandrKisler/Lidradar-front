# Codex · Роли и продолжение работы Claude

Дата: 29.10.2026. Основание: поручение владельца подготовить для Codex аналог
структуры Claude из коммитов `3844681` и `c9e676d`, чтобы продолжить незавершённое.
Настройка не означает, что frontend уже исправлен или принят.

## Роли и модели

| Роль                     | Модель / effort        | Назначение                                                   |
| ------------------------ | ---------------------- | ------------------------------------------------------------ |
| Основная сессия          | `gpt-6.1-sol` / medium | Код, тесты, интеграция, общие файлы и handoff                |
| `lidradar-qa`            | `gpt-6.1-sol` / high   | Независимые TEST, затем FUNCTIONAL на готовом снимке         |
| `lidradar-visual-review` | `gpt-6.1-terra` / high | Просмотр Figma/browser изображений, три результата адаптивов |
| `lidradar-worker`        | `gpt-6.1-sol` / medium | Опциональная независимая реализация в переданных файлах      |
| `lidradar-explorer`      | `gpt-6-luna` / high    | Опциональная узкая карта кода/контракта/findings без правок  |
| `lidradar-expert`        | `gpt-6-astra` / high   | Только явная ограниченная консультация, без реализации       |

Это проектный выбор моделей. Обычный цикл сохраняет трёх участников из
последнего Claude-коммита; worker/explorer/expert не добавляются к каждому этапу.
Команды выполняются инструментами, отдельный агент только ради `npm` не нужен.
Основная сессия координирует работу и сама разрабатывает; отдельного менеджера нет.

`.codex/config.toml` задаёт основной профиль и максимум три одновременно
открытых субагента, не считая ведущего. Никаких вложенных агентов.
Узкие роли находятся в `.codex/agents/*.toml`. Проверяй модель и effort
фактической сессии: уже открытый чат может сохранить свой выбор. Не подменяй
недоступную модель молча и не меняй глобальные настройки/auth/provider.

В клиенте без выбора custom agent передай инструкции соответствующего TOML
через поддерживаемый инструмент субагентов, явно выбрав модель/effort и короткий
brief. При разных моделях создавай независимый контекст (`fork_turns="none"`,
если инструмент предлагает этот параметр). При отсутствии субагентов выполняй
разрешённый код сам, а независимую приёмку оставляй UNVERIFIED.

## Независимость и порядок

1. Ведущий сверяет текущий код, AC, checkpoint и открытые findings. На каждый
   сценарий создаёт brief по [шаблону](CODEX-TASK-BRIEF.md).
2. Независимые исследования/правки можно делегировать параллельно только с
   непересекающимися write sets. Передача владения явная. Shared primitives,
   generated/schema, lockfile, общая регистрация и STATUS остаются у ведущего.
3. Ведущий интегрирует результат, выполняет адресные проверки и сохраняет
   snapshot: HEAD, список всех inputs и их SHA-256, включая новые файлы.
   Одного `git diff` недостаточно: untracked в него не входят.
4. На неизменном snapshot QA выполняет тесты, затем отдельно проверяет смысл
   тестов и все AC. TEST PASS сам по себе не означает FUNCTIONAL PASS.
5. Только после обоих PASS UI проверяет готовые изображения всех устройств.
   На этом этапе ведущий и workers не меняют inputs; один владелец browser/preview.
6. Finding возвращается ведущему. Исправление создаёт новый snapshot; повторяются
   затронутые проверки и обязательные финальные gates из WORKFLOW.

Если поменялись inputs, проверка старого снимка остаётся исторической.
QA может создавать только логи/отчёты в переданном каталоге artifacts; не исходники,
тесты, конфиг или baselines. UI/explorer/expert не меняют файлы. Эти ограничения —
инструкции ролей: субагенты наследуют sandbox/approval родителя, отдельной
технической read-only изоляции TOML не создаёт. Не обходи ограничения через shell.

Не параллелить US-M01-01 и US-M01-02 как двух авторов RegisterForm/flow.
Три viewport не требуют трёх одинаковых агентов. Отдельный функциональный
reviewer не дублирует QA в штатном цикле. После двух неудачных исправлений одной
причины собери диагностику; автоматической эскалации на Astra нет.

новый старт Codex; используй [CODEX-START](CODEX-START.md).

Проверяй их фактическое состояние, не переписывай готовую регистрацию.

Результаты R1 и checkpoint не перезаписывай; новый круг имеет свой каталог/manifest.

## Среда и доказательства

Живой путь: локальный `npm run dev:stage` → существующий Vite proxy →
`https://stage.app-lid-radar.ru`. Локальный backend 8080/8081 не нужен.
Перед stage QA проверь revision, готовность и миграцию
`000032_registration_invitation_check`. Сохранённая база — backend
`0d06d96b62b03947e6cda10615c8c57324a479f4`, OpenAPI SHA-256
`9f9766cc4d23e398268aabc68d8adae6db9bf3358bf14953b151f36c617e3027`;
для потомка проверь фактический контракт, не считай старый hash текущим автоматически.
Не меняй backend/миграции/режим A/C и не сбрасывай общие данные или лимиты.

Unit/mock/visual fixtures локальные и синтетические. Stage, доставка писем,
Telegram и пользовательская приёмка — отдельные виды evidence. Credentials
не печатать; `.env.stage.local` использует сервер Vite, не переносить в `VITE_`.
Перед живым stand-прогоном учти cookie `lidradar_stage_session` и выделенные
accounts из ACCESS-RESUME; массовые негативные сценарии проверяй mocks.

Figma только читать. Переиспользуй сохранённые exports/source-map/hashes.
Точные frames, состояния, viewport, fixture, browser/version, scale, шрифты
и revision обязательны. UI должен реально просмотреть изображения; отсутствие
доступа или нечитаемый кадр означает UNVERIFIED. Общий UI PASS требует трёх PASS.

В цикле — адресное воспроизведение и затронутые проверки, на готовом этапе —
все обязательные gates WORKFLOW. Не повторяй успешный полный suite без изменения
inputs/нового основания. Не ослабляй budgets, coverage, assertions и baselines.
Логи/PNG/diff храни в artifacts, в Git — компактные manifest/отчёты без секретов.
В handoff фиксируй snapshot, команды/exit codes, findings и следующий шаг.
Расход подписки не равен стоимости API; экономию без измерений не обещать.
