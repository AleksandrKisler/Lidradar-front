## Работа и субагенты

- Обычный цикл: основная сессия пишет код → `lidradar-qa` выполняет TEST,
  затем FUNCTIONAL → `lidradar-visual-review` принимает desktop/tablet/mobile.
  Модели и инструкции ролей заданы в `.codex/agents/*.toml`.
- Делегируй независимые ограниченные задачи, когда это сокращает работу.
  `lidradar-explorer` собирает контекст; `lidradar-worker` получает конкретные
  файлы и критерии готовности. Малую или зависимую задачу выполняй сам.
- Перед делегированием заполни `docs/frontend-v2/CODEX-TASK-BRIEF.md` как шаблон
  отдельного brief в artifacts. Передавай пути и relevant diff, не всю историю.
- У каждого файла один автор. Общая регистрация US-M01-01/02, API generated,
  shared primitives, lockfile и STATUS принадлежат ведущему. Не отдавай двум
  авторам одну форму/модель. Сначала интеграция, затем заморозка и независимый QA.
- На проверяемом снимке запрещены правки inputs. QA не меняет код/тесты,
  UI читает готовые изображения. После исправления — новый снимок и затронутые проверки.
- Не запускай вложенных агентов, постоянного менеджера и дополнительные чаты.
  Не вызывай Astra автоматически: `lidradar-expert` — явная узкая консультация.
- Перед сжатием контекста обновляй STATUS: сделано, снимок, evidence, открытые
  findings, следующий шаг. При смене Claude/Codex передавай владение файлами.

## Границы и проверки

- Правь frontend, его тесты и документацию. Не переопределяй backend/API,
  бизнес-правила, роли, деньги и lifecycle. Не меняй Figma или production.
- Не затирай чужие изменения; не делай reset/stash/checkout поверх dirty tree.
  Push/deploy/merge требуют отдельного поручения. Не читай секреты для визуальной
  работы; не выводи credentials/cookie/invite codes и не коммить `.env`.
- Node — из `.nvmrc`, package-lock сохраняется. В цикле — адресные тесты и
  typecheck; обязательные финальные gates и browser matrix — по WORKFLOW.
- Живой QA: `npm run dev:stage` → backend-stage через существующий proxy.
  Сначала проверь revision/API hash/миграцию. Локальный backend не требуется.
  Mock/visual fixtures и stage учитывай раздельно; реальные письма/Telegram
  проверяй только в разрешённом тестовом контуре, без сброса общих данных/лимитов.
- Не ослабляй assertions, coverage, bundle budgets или baselines ради PASS.
  Визуальный PASS требует просмотра реальных browser/Figma изображений всех
  трёх адаптивов. Нет доказательства — UNVERIFIED; лимит ходов не означает PASS.
- Обычные разрешённые локальные правки не требуют повторного подтверждения.
  Блокировка одного сценария не останавливает независимые разрешённые задачи.
- Итог: story IDs, файлы, команды/exit codes, snapshot, evidence, результаты
  TEST/FUNCTIONAL/UI, ограничения и следующий шаг. Не утверждай запуск без запуска.
