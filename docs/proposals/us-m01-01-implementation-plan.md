## Результат по сценариям

| Сценарий | Интерфейс                                                                                                      | Серверная зависимость                                                            |
| -------- | -------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| A        | `/register`, имя/email/password без кода; «Использовать код приглашения» → B2                                  | Существующие GET режима и POST без `inviteCode`, только `open`                   |
| B        | `/register?flow=invite`, B2 код → B3 данные; «Использовать другое приглашение» сбрасывает проверку/пароль → B2 | Новый POST проверки, затем прежний POST с `inviteCode` и окончательной проверкой |
| C        | `/register`, warning над отключённой формой; активны приглашение/login/legal, C2 → B2                          | `invite_only` из GET режима и серверный запрет регистрации без кода              |

Одна страница, один маршрут, общая форма данных. Новый глобальный store,
frontend ENV и запуск по календарю не нужны. После успеха — `/auth/me`
и существующий boot-путь по членствам и `canCreateOrganization`.
Письмо сервер инициирует независимо от онбординга; frontend его не дублирует.

## Согласованные технические настройки

| Решение               | Значение                                                                                                                           |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| API                   | `POST /api/v1/auth/registration/invitation/check`, `{ code }`, успех `204` без тела/cookie                                         |
| Непригодный код       | Только `403 INVITATION_INVALID` даёт красное состояние с `!`; сеть, Origin-отказ и прочие ошибки не означают негодность кода       |
| Постоянный лимит      | `REGISTRATION_INVITATION_CHECK_IP`, 10 попыток/15 минут; нужна backend-миграция CHECK допустимых scope                             |
| Автопроверка          | 400 мс после полного корректного значения; Enter/стрелка через ту же команду, один запрос, без автоповтора после ошибки            |
| Контекст B            | Память + sessionStorage вкладки `{ code, checkedAt }`, 30 минут без продления при F5; перед B3 обязательная серверная перепроверка |
| Ссылки                | `/register?code=…` и `/register?flow=invite&code=…`; код убрать из query, оставить `flow=invite`                                   |
| Режим                 | Перечитывать при входе на обычную регистрацию, не открывать A из старого кеша до ответа; ошибка с явным повтором                   |
| Финальный отказ кода  | Вернуть B2 с красным `!`, сбросить пароль/подтверждение; имя/email допустимо удержать в памяти                                     |
| Сбой после `201`      | Успех аккаунта фиксируется до `/auth/me`; повторяется только загрузка сессии                                                       |
| Потерянный ответ POST | Без автоматического повтора регистрации: сначала `/auth/me`, затем существующий вход/восстановление при неизвестном исходе         |

Точные ошибки, нормализация, служебные подсказки, очистка/TTL и отсечение
поздних ответов описаны в едином согласованном пакете. Технические настройки
приняты вместе с решением; нумерация 35 продуктовых AC сохраняется.

## Зависимости и поставка

Пакет не снимает ограничения [стабильного релиза](../frontend-v2/RELEASE-SCOPE.md).
Решение и ADR согласованы; перед поставкой определить релиз расширения. Далее backend,
миграция, серверный контракт, проверка endpoint в разрешённой среде;
после этого — frontend и его приёмка.

Синхронизация после backend OpenAPI, из frontend:

```sh
npm run api:sync -- /Users/aleksandrkisler/Develop/LidradarWorksapce/Lidradar
npm run api:generate
npm run api:check
```

Generated-файлы вручную не править. До контракта не добавлять вымышленные
endpoints или mock-успех в runtime; проверка длины и пробная регистрация
не заменяют precheck. Старый клиент с `inviteCode` остаётся совместимым
с новым backend; новый frontend требует доступного метода.

Порядок проекта сохраняется: Claude реализует frontend, Codex проводит
приёмку. Реализация frontend, делегирование и пересылка задания сейчас не начаты.
